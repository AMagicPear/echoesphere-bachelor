## 一、设计与实现的边界仍有残余模糊

你已把大部分技术细节放到了第4章，但**第3.2.3节“旅人人物形象设计”**仍然跨界。这一节现在包含了完整的技术流程：ChatGPT生成概念词→NanoBanana生成形象→Seed 3D生成OBJ→Blender骨骼绑定和动画→Unity输入控制脚本。对于一篇工科学位论文，**这些属于第4章的“虚拟场景与角色构建”内容**。

**具体问题**：你在第3章用一段话概括了五个阶段，然后第4章却只讲TravelerController的移动脚本——骨骼绑定、动画状态机的具体配置完全没有出现。这让评阅人困惑：旅人的动画到底怎么驱动的？Blender导出的FBX如何接入Unity Animator？这些技术细节不应在设计章一笔带过。

**修改建议**：将3.2.3大幅精简，只保留概念形象（含“那位没有过去…”的诗意引语）和旅人作为交互主体的设定。把“使用Seed 3D生成模型→Blender骨骼绑定→Unity动画状态机”这一段完整移到第4章，在4.3.1之前新建**4.3.1 旅人角色的建模与动画实现**，再紧跟“旅人控制器与虚拟输入设备”为4.3.2。这样才符合“设计说What，实现说How”的边界。

## 二、测试章节缺乏量化数据——这是最致命的硬伤

第5.3节“系统测试”列出了测试目的和用例表，但全部测试结果只用一句话带过：“经逐一验证，所有用例均通过，系统运行稳定。” **这在工科论文中是完全不合格的。** 你作为数字媒体技术专业的学生，必须用数据说话。

用例1要求“端到端延迟<100ms”，实际测出来是50ms还是90ms？用例2要求“间隔不低于500ms”，实际节流间隔是多少？用例7灯光模式切换延迟要求<200ms，实际呢？更严重的是，**你没有给出任何压力测试或帧率数据**。Unity场景在山峦抖动、草地渲染同时收到灯光指令时的帧率维持情况完全空白。

**修改建议**：立即在5.3节补充**测试结果表**。例如：

| 测试用例 | 实测延迟 | 预期指标 | 是否通过 |
|:---|:---|:---|:---|
| 手势指向→角色移动 | 67ms (n=50) | <100ms | ✓ |
| 表情变化上报间隔 | 512~780ms | ≥500ms | ✓ |
| 灯光模式切换 | 148ms | <200ms | ✓ |
| Unity场景帧率（复杂场景） | 47fps | >30fps | ✓ |

同时给出测试方法：延迟如何测量（网络抓包？Unity日志时间戳？），数据采集了多少组。**没有数据的测试章等于没有。**

## 三、交互体验评估写成了对比分析，偏离了验证目标

你现在第5.4节的标题是“交互体验评估”，但内容完全是与Phillips目标导向交互框架的对比分析。这更适合放在第2章或第6章讨论，**不应作为独立的评估章节存在**。

交互体验评估的常规做法有两种：一是客观指标（任务完成时间、错误率、路径效率），二是主观量表（SUS系统可用性量表、情感体验问卷）。你两者都没有，却用方法论对比充数。

**修改建议**：如果你确实没有条件做用户测试，则**立即修改章节名称**，将5.4标题改为“与目标导向交互方法的对比讨论”，并入第6章“总结与展望”作为一节，或者移至第2章作为方法论讨论。如果保留在第5章，则必须补充哪怕是小规模的体验反馈（3-5人试用后填写SUS量表或简单访谈）。这关乎论文的完整度。
