\begin{chineseabstract}
随着虚拟现实、人工智能等数字技术的快速发展，人机交互正逐步从以键盘、鼠标为主的单一输入范式，转向融合多感知通道的沉浸式交互形态。然而，当前实体展览中的公共交互装置仍存在交互方式趋同、情感反馈缺失、体验深度不足等问题。本文针对上述问题，设计并实现了一套面向实体展览的沉浸式多模态交互系统。系统以Unity引擎为核心交互平台，整合了手势识别、面部情绪识别、交互应用状态感知等多源信息，并基于大语言模型智能体构建中央决策模块，实现对虚拟场景与物理LED灯阵装置的协同控制。本文详细阐述了系统的总体架构、网络通信协议、智能体工具调用机制、关键视觉与交互模块的实现方法，并展示了实体装置的设计与集成。本系统为构建更具情感连接与沉浸感的公共展览交互体验提供了可行的技术路径与设计参考。

\chinesekeyword{多模态交互；游戏引擎；智能体；情感计算；实体展览}
\end{chineseabstract}

\begin{englishabstract}
With the rapid development of digital technologies such as virtual reality and artificial intelligence, human-computer interaction is gradually shifting from a single input paradigm dominated by keyboards and mice to an immersive interaction paradigm that integrates multiple sensory channels. However, current public interactive installations in physical exhibitions still suffer from homogenized interaction methods, lack of emotional feedback, and insufficient experience depth. To address these issues, this thesis designs and implements an immersive multimodal interaction system for physical exhibitions. The system uses Unity engine as the core interaction platform, integrating multi-source information such as gesture recognition, facial emotion recognition, and application state perception, and constructs a central decision-making module based on large language model agents to achieve coordinated control of virtual scenes and physical devices of LED arrays. This thesis elaborates on the system's overall architecture, network communication protocols, agent tool-calling mechanisms, implementation methods of key visual and interaction modules, and demonstrates the design and integration of physical devices. This system provides a feasible technical path and design reference for constructing more emotionally connected and immersive public exhibition interactive experiences.

\section{研究背景}

在日常的数字交互中，无论是个人电脑上的电子游戏，还是移动设备上的各类应用，人们的交互方式长期依赖键盘、鼠标、手柄或触摸屏等传统输入设备，而系统的反馈也大多局限于屏幕内部的视觉变化与扬声器发出的音效；而另一方面，当谈及沉浸式体验时，公众的第一反应又往往将其与虚拟现实头戴设备联系在一起，似乎只有将用户从物理空间中完全剥离、置入一个由头戴式设备构建的虚拟环境，才能冠之以沉浸。然而，这种将沉浸式体验与虚拟现实等同的认知恰恰忽略了实体空间自身的不可替代性。在博物展览、公共艺术装置等实体展览场景，参观者切身在场，能够自然地与物体展览装置交互、自然地接受全方位的声音、光效，其多感官协同的体验是任何虚拟现实设备都无法完全复现的。这也使得多人共享体验以及更深刻的情感联结成为可能。

从当今实体展览的现状看，其也正亟待引入更具沉浸的交互方式。公共交互装置作为现代城市空间与博物展览中的新兴艺术表达媒介，致力于构建人与作品之间的深度对话\citing{wen2022huadong}。当今的展览模式正逐渐从藏品陈列和静态信息呈现，向强调观众参与和体验感受的方向演进，博物馆等机构持续致力于优化其与观众的互动方式，特别是在观众与文物、艺术品等展品的交互层面，当代博物馆与艺术展厅致力于打破“请勿触摸”的传统禁锢，转而追求更具实践性、叙事性与沉浸感的互动体验\citing{ogrizek2024vr}\citing{jiang2024dunhuang}\citing{pietroni2025multisensory}。但遗憾的是，当前展览中的公共交互装置在交互体验上仍存在明显不足：一方面，部分系统仅简单引入数字屏幕与触控交互，参观者的体验与操作普通电子设备无异，未能充分发挥实体展览特有的现场感与空间优势；另一方面，由于设计范式趋同，许多装置的交互方式、反馈逻辑与视觉表现呈现同质化倾向，难以有效促进参与者的情感提升\citing{wen2022huadong}与持续探索，导致可互动但不耐体验的现象。这使得互动装置未能充分实现其作为展览媒介应有的情感沟通与意义建构价值，观众与作品之间难以建立稳定而深入的联系。

事实上，此前已经有一些先锋艺术家和商业团体曾尝试将沉浸式体验带入真实物理空间，但这些探索大多发生在人工智能技术爆发式跃迁的前夜，其交互逻辑仍受限于预设规则。而近两年来，多模态大模型的飞速发展，尤其是2026年初，以OpenClaw为代表的个人终端智能体火爆互联网的当下，这种根植于现实空间的沉浸式体验或将迎来新的可能。

\section{研究目的和意义}

本课题旨在借助人工智能与智能体技术，将游戏引擎与其所支撑的高品质沉浸式交互体验带到实体展览空间之中，为此设计并实现了一套沉浸式多模态交互系统框架及其配套交互应用《回声之境》。具体而言，本课题探索了一种将手势与面部表情纳入输入模态、将多模态智能体作为核心理解模块、将现实空间中的灯光装置变化与屏幕空间内的动态视觉生成协同作为输出反馈的新型交互范式。参展者的手势动作与面部情绪表现被实时感知，驱动虚拟场景内的角色移动和视觉动效生成，同时通过物理灯光装置将这种变化延伸至实体展览空间，使沉浸感从虚拟空间扩散至实体空间。

人类的情感状态与行为意图天然地外化于面部表情、手势与身体姿态之中。深度学习在计算机视觉与运动捕捉领域的持续突破，使得对这些具身化信号的实时捕获与高精度解析已经非常成熟。借助Google推出的MediaPipe解决方案，可在Android、iOS、网页和Python应用中快速应用手势识别、面部特征点检测等任务\citing{google2024mediapipe}。ReAct范式\citing{yao2023react}提出了一种新的方法，通过结合语言模型中的推理（reasoning）和行动（acting）来解决多样化的语言推理和决策任务。这提供了一种更易于人类理解、诊断和控制的决策和推理过程，赋予了多模态智能体跨模态理解、任务规划与工具调用的综合能力\citing{durante2024agent}。多模态情感识别领域研究表明融合面部表情与身体姿态等多通道信号能够显著提升情感理解的准确性与鲁棒性\citing{tao2024multimodal}，而本课题进一步将这些信息延伸为实体环境中的具身化反馈，使得手势与表情成为人机之间更自然、且具备语义和情感信息的沟通语言。

在交互应用的开发平台的选择上，Unity引擎凭借其成熟的实时渲染管线、场景管理系统与物理模拟能力，能够在消费级硬件上维持交互帧率下的高品质视觉输出。更为关键的是，游戏产业在数十年的发展历程中积累了丰富的空间交互、叙事引导与即时反馈的设计经验，这些经验可以在一定程度上反哺展览系统的交互设计\citing{kruger2024gameengines}，使展览体验获得游戏般的趣味性与沉浸度。

本课题通过智能体的统一调度，将参观者的手势和情感信息、虚拟场景的视觉生成与现实环境的灯光纳入同一控制闭环，使三者协同变化、彼此呼应，构建出一种屏幕内外相互渗透、虚实联动的沉浸式体验。围绕实体展览场景开展设计研究，对于探索在人工智能时代下的新型人机交互以及游戏引擎在非游戏场景中的应用具有重要的现实意义。

\section{数字表演与沉浸式展览}

一套完整的博物馆交互展览系统通常包含数据层、逻辑层与展示层三层架构，其中，展示层负责提供高保真的三维渲染与多模态交互界面，支持用户在实体空间中以多样方式与虚拟内容互动\citing{li2024exhibition}，也是本课题所关注的层级。

互动装置艺术作为连接展览内容与观众的关键媒介，其价值不仅在于满足基础的视听需求，更在于营造用户在参与过程中生理、心理乃至精神层面的综合情感体验。数字技术在为表演提供新的技术手段的同时,也帮助表演进一步打破了固有的等级制度和观演关系的桎梏\citing{lu2024digital}。在数字表演中，表演者/创作者往往是隐身的，观演者切实通过自己的行为构建表演中的互动性\citing{lu2024digital}。早期范例如《蜡网》（Waxweb），一部大卫·布莱尔执导的电影《蜡或蜜蜂中的电视发现》（Wax or the Discovery of Television Among the Bees）的超媒体版本。它是一部时长 85 分钟、由 8 万个片段组成的电影。观众被赋予随意开始演出、左右叙事走向、切断演出与回顾演出的权力，展示出计算机和互联网技术让新型的互动型观演成为可能\citing{lu2024digital}。

数字表演中的实时性、参与性互动在虚拟现实技术中被进一步深化，观者的参与性也从架上时期的“画外”升华到虚拟现实的“画内”。蒋旎等人围绕敦煌艺术展开的沉浸式展览实践为这一方向提供了具体参照：在“遇见当代飞天”主体展演空间中，随著参观者位置移动, 在投影区域的相应位置会实时出现雷达交互后的粒子渲染画面，这种多重叠加的视觉效果为观者营造了丰富的沉浸式感受\citing{jiang2024dunhuang}。

在国外，Pietroni等学者通过整合通用设计原则、先进技术和高感官体验，采用多通道传播策略，同时通过视觉、听觉和触觉通道传递信息，使博物馆对具有不同身体、认知和社会需求的参观者具备更好的无障碍体验\citing{pietroni2021accessibility}；其近期研究进一步围绕体验设计与真实感新视角，深入探讨了数字化、传播策略、互动机制、创意叙事、沉浸式技术及可及性议题的方法论路径，并提出现代博物馆应借助多媒体和实体数字融合技术，让实物与数字内容共存，创造认知和情感上都能深度参与的体验\citing{pietroni2025multisensory}。

互动仪式链理论从互动行为本身的视角, 探讨互动仪式对互动装置参与者体验感的影响和积极共鸣带来的情感提升，为制作互动装置提供了理论框架\citing{wen2022huadong}。如图\ref{fig:ritual}所示，温文龙等学者指出，通过预设具有规范性、表演性与趣味性的互动仪式，可以为参与者创造特定的体验情境。在仪式化的互动过程中，情感能量得以产生、分享与传递，并通过“仪式链”的连续性维持高强度的参与体验。

\end{figure}

而在具体的设计语言层面，情感化设计将人的情感需求置于设计的首位\citing{norman2005emotional}。李静雅等人通过TouchDesigner软件实验，提出了节奏与视觉形态关联的音乐可视化模型——圆形对应慢节奏、方形对应中节奏、三角形对应快节奏\citing{li2023music}，为视听联觉反馈提供了可操作的映射规则。Valérian Fraisse等人则从艺术意图、交互设计与系统设计三个视角出发，提出了描述交互式声音装置的概念框架\citing{fraisse2021sound}。实体工具在沉浸式交互中的作用同样值得关注：研究表明，在博物馆VR交互中为复杂任务提供实体操作工具能对用户体验产生积极影响\citing{ogrizek2024vr}。

总体而言，数字表演与沉浸式展览的发展历程清晰地勾勒出一条互动性不断深化的轨迹——从互联网艺术赋予观众的叙事选择权，到VR技术实现的身体在场性，再到AI驱动下由观众行为实时生成的视觉响应，每一次技术进步都在拉近观者与作品之间的距离。这一演进方向也促成了本课题构建一个能够感知参展者行为与情绪、并据此实时生成个性化视觉与物理反馈的交互系统的设计目标。

而在当今，经过数十年的技术演进，游戏引擎已发展为构建沉浸式虚拟环境的重要工具。在本课题所关注的展览交互场景中，游戏引擎的价值体现在两个层面，一方面程序化视觉生成技术能够根据实时输入参数驱动视觉元素的形态、颜色与运动规律变化，实现个性化、响应式的展览视觉体验；另一方面引擎本身即是成熟的交互框架，游戏产业数十年积累的空间交互、叙事引导与即时反馈设计经验，可以直接转化为展览系统的交互设计资源。

程序化视觉生成技术利用算法动态创建视觉内容，在现代游戏设计与计算机图形学中常用于高效生成地形、纹理或动态效果。该技术能够根据实时输入参数驱动视觉元素的形态、颜色与运动规律变化，从而实现内容表现的无限多样性与自适应特性，非常适合用于创造个性化、响应式的展览视觉体验。Unity与Unreal Engine等引擎提供了强大的图形渲染、物理模拟、音频处理与脚本逻辑支持，极大地降低了复杂交互应用的开发门槛，并已广泛应用于数字展览和互动艺术领域\citing{kruger2024gameengines}。Unity引擎以C\#作为脚本语言控制对象行为与系统流程\citing{chen2024u3d}。在视觉渲染层面，Unity配合Shader编程可实现光影、粒子、后期处理等沉浸式空间效果\citing{feng2016unityshader}。为提高展览场景中的渲染效率，动态批处理、静态批处理与LOD等优化手段可将渲染开销控制在目标帧率以内\citing{chen2024u3d}。

此外，Unity 具备卓越的外部设备扩展能力，已经成为连接物理装置与感知模块的多维集成平台。它不仅能通过专用 API 与 LeapMotion 等高精度感知硬件实现毫秒级数据同步\citing{ni2024leapmotion}，更能够接入多种外部系统与工业级协议，应用于数字孪生与机器人仿真等复杂场景中。在数字孪生领域，徐曼菲等人针对火工品装配车间的数字化改造需求，以 Unity3D 为核心构建了数据采集、数据管理、数字化建模与功能集成四层架构，实现了物理车间装备与虚拟模型的状态同步监控\citing{xu2026digitaltwin}。在机器人仿真领域，汤沁怡将 Unity 与博物馆导览机器人相结合，设计了虚拟博物馆场景下的阿凡达式机器人系统，通过 TCP 通信建立 ROS 与 Unity 的高速数据通道，机器人端 AMCL 定位发布的位姿数据经坐标系转换后实时驱动 Unity 中虚拟仿真模型的运动，并通过插值算法优化运动视觉效果，结合 HTC VIVE 头盔为用户提供兼具远程呈现与遥操作能力的沉浸式漫游体验\citing{tang2022avatar}。周骞等人设计的 Unity-ROS 协同仿真系统则面向无人平台导航验证，通过 Socket 通信实现运动控制建模与多模态传感器仿真的跨平台交互\citing{zhou2021unityros}。这些实例都验证了 Unity 在工业实时数据驱动场景中的适用性。

\section{多模态智能体技术}

ReACT范式\citing{yao2023react}奠定了现代智能体的核心工作模式。其关键洞察在于将推理（thought）本身也视为一种动作——将语言空间$\mathcal{L}$与原始动作空间$\mathcal{A}$合并为增强动作空间$\hat{\mathcal{A}} = \mathcal{A} \cup \mathcal{L}$，使得模型可以在推理与行动之间自由切换，如公式(\ref{eq:react})所示：

\begin{equation}
\hat{a}_t \sim \pi(\hat{a}_t \mid c_t), \quad c_t = (o_1, a_1, \cdots, o_{t-1}, a_{t-1}, o_t)
\label{eq:react}
\end{equation}

其中$c_t$为截至时刻$t$的交互上下文，包含所有历史观测与动作；$\hat{a}_t \in \hat{\mathcal{A}}$为策略$\pi$输出的增强动作，当$\hat{a}_t \in \mathcal{L}$时为推理思维（不影响外部环境但向上下文中注入分析信息），当$\hat{a}_t \in \mathcal{A}$时为外部动作。上下文随交互推进而累积更新：$c_{t+1} = (c_t, \hat{a}_t, o_{t+1})$。这一范式使智能体形成了“感知—推理—行动—反馈”的闭环。然而，早期智能体的交互范围主要局限于文本层面，而真实世界的展览交互系统通过图形界面运行，智能体若不能理解视觉界面，其行动能力便极为受限。

而近两年兴起的GUI智能体突破了这一限制，如CogAgent\citing{hong2024cogagent}。作为一个180亿参数的视觉语言模型，它直接从屏幕截图中理解GUI元素——包括微小图标、文本标签与空间布局——而无需HTML等结构化元数据。其核心设计是高低分辨率双分支架构：224×224低分辨率分支负责整体场景理解，1120×1120高分辨率分支通过交叉注意力模块精确识别细小文本与界面组件，从而在不显著增加计算开销的前提下兼顾全局感知与局部精度。在PC端Mind2Web与安卓端AITW基准上，仅使用屏幕截图的CogAgent超越了使用提取文本的纯语言模型方法，证明了智能体可以通过与人类相同的视觉通道感知数字世界。

如果说GUI智能体的挑战在于理解平面界面，那么三维交互环境中的实时多模态决策则是更高的门槛——决策延迟与交互流畅性之间存在天然张力。Lumine\citing{tan2025lumine}首次实现了在这一约束下的突破：作为一个端到端的视觉-语言-动作模型，它在《原神》中以5Hz频率接收屏幕像素、30Hz频率输出键盘与鼠标操作，完成了小时级主线任务的实时通关。其关键创新是混合思考（hybrid thinking）策略——受认知科学双过程理论启发，智能体仅在遇到复杂决策或异常状态时才进入显式推理模式，在多数常规场景中直接输出动作，从而带来25.3倍的端到端延迟优化。Lumine采用三阶段递进式训练（1731小时人类数据预训练→200小时指令跟随→15小时推理数据），且仅在《原神》上训练的模型即可零样本泛化至《鸣潮》和《崩坏：星穹铁道》，证明了其习得的是真正的场景理解能力而非记忆。Game-TARS\citing{wang2025gametars}从大规模预训练维度提供了独立验证：在超过5000亿token的跨游戏数据上预训练后，其在Minecraft开放世界任务上的成功率约为先前最佳方法的两倍。

上述工作共同验证了一个对本课题具有支撑意义的命题：经过适当设计与训练的智能体，确实能够理解交互应用中的复杂视觉场景并在实时约束下做出多模态决策。

在确立了智能体的感知与决策能力之后，如何将其嵌入有结构的交互流程是展览场景面临的下一个问题——展览互动不是无目的漫游，而需沿着预设的情感叙事线索推进。Phillips等人提出的目标导向交互框架\citing{phillips2025goal}为此提供了一种值得借鉴的思路：将交互场景建模为拼图图（puzzle graph）$G = (V, E)$，节点代表关键的情境里程碑，边代表合法的状态转移路径，状态转换由设计者为每条边预设的封闭式问题集$Q_{v \rightarrow v'}$驱动，如公式(\ref{eq:state})所示：

\begin{equation}
s_{t+1} = v' \quad \text{if} \quad \mathcal{L}\Big(\big\{\text{QALM}(H_t, q) \mid q \in Q_{v \rightarrow v'}\big\}\Big) = \text{True}
\label{eq:state}
\end{equation}

其中$H_t$为截至当前的完整对话历史，QALM作为问答语言模型对问题集中的各项逐一评估，$\mathcal{L}$为设计者指定的逻辑聚合函数。该框架的核心思想在于将对话生成与状态追踪解耦，使叙事推进独立于自由对话。这一思路启发了本课题的系统架构：《回声之境》中，MediaPipe承担感知任务，VLM集中于推理与决策，情感状态图（迷茫$\rightarrow$锚定、碰撞$\rightarrow$边界、敬畏$\rightarrow$自由）则提供了结构化的叙事引导框架，其节点与边的组织方式与拼图图逻辑一致。

在多模态感知维度上，情感计算是展览交互中不可或缺的组成部分——智能体不仅需要理解“参展者做了什么”，还需感知“参展者处于何种情绪状态”。Thebaud等人\citing{thebaud2024multimodal}的实验表明，语音、文本与视觉三种模态的融合在所有核心情感维度上均一致优于单一模态。MiSTER-E等框架进一步采用专家混合架构\citing{durante2024agent}，通过门控机制根据信号可靠性动态调整模态权重，使系统在复杂环境中维持情感推断的稳定性。大语言模型还能结合交互历史推理情感的深层语义，从而在表层表情识别之上提供更精准的交互策略调整。

总体而言，从ReACT奠定的推理-行动范式，到CogAgent实现的视觉界面理解，再到Lumine与Game-TARS在实时三维交互中验证的多模态决策能力，最后到目标导向交互框架提供的结构化叙事设计方法，这些研究逐步让智能体成为感知、理解并回应参展者情感状态的交互伙伴。

\chapter{需求分析与总体设计}

\section{系统需求分析}

\subsection{项目需求概述}
随着多模态感知技术与大语言模型的快速发展，实体展览正从传统的静态展示向沉浸式交互体验转型。本课题旨在构建一套沉浸式多模态交互系统以及名为《回声之境》的交互应用。该系统融合手势识别、面部情绪分析与智能体，以情感状态变化驱动虚拟场景与物理装置的联动响应，引导参展者经历叙事化展览体验。 

在功能性需求方面，该系统需要具有以下功能：

\begin{enumerate}
\item 全流程多模态。输入层需实时捕捉参展者多源行为数据；理解层需调用大语言模型对多源感知信息进行语义推理，完成对参展者当前意图与情感状态节点的量化评估；反馈层需基于输入和智能体的决策结果，实时驱动虚拟场景中的视觉生成，并同步驱动实体空间中的灯光控制，构建闭环的沉浸式交互链路。
\item 全流程状态机管理。系统需维护一套完整的叙事状态机，根据多模态输入的推理结果触发状态跳转。系统应能准确记录用户在交互流程中的当前进度，确保叙事体验的逻辑连续性。
\end{enumerate}

在非功能性需求方面，该系统需要达到以下要求：

\begin{enumerate}
\item 架构灵活性与可扩展性。系统应采用松耦合的模块化架构，各功能模块通过统一的自定义JSON协议和TCP连接进行通信。当需要接入新的输入或输出模块时，例如语音、深度摄像头、MIDI键盘等，仅需实现协议即可完成扩展，无需大规模修改核心逻辑，从而降低迭代维护和推广到其他应用场景的成本。
\item 完善的调试工具。鉴于多模态链路长且包含模型黑盒，系统需内置完善的运行状态监控与调试工具，支持实时追踪智能体推理逻辑、回溯关键决策日志，并应提供专用的调试客户端进行指令模拟，以增强系统的鲁棒性。
\item 延迟和性能要求。展览交互系统的沉浸感与流畅性直接依赖于系统的响应速度。多模态输入和输出的反馈应控制在100ms以内，而智能体推理决策的反馈应控制在10s以内，以提供流畅、即时的交互体验。
\item 用户交互友好性。系统的交互设计需兼顾不同年龄、文化背景与技术熟悉度的参展者，确保交互界面直观易懂，操作流程自然流畅。
\end{enumerate}

\section{系统概要设计}

\subsection{总体架构}

\begin{figure}[htbp]
  \centering
  \includegraphics[width=1.0\textwidth]{pic/系统总体架构图.pdf}
  \caption{系统总体架构图}
  \label{fig:system-arch}
\end{figure}

以上述需求为指导，本系统最终形成了如图\ref{fig:system-arch}所示的“感知—理解—反馈”三层架构。理解层由EchoAgent与TCP服务端组成，是系统的通信中枢与决策核心，感知层与反馈层均以TCP客户端接入。感知层负责采集多源数据并上报，反馈层负责接收决策指令并执行。MediaPipe客户端归属感知层，树莓派客户端归属反馈层，Unity客户端则同时属于感知与反馈两层。

感知层、TCP服务端和EchoAgent之间以生产者-消费者模式设计，即感知层的每个模块各自的TCP客户端都会把实时产生的交互数据发送到TCP服务端。EchoAgent每隔一个固定间隔（默认设置5s）查阅一次消息，而TCP服务端同时也可以跳过EchoAgent直接处理一些简单的命令转发。

系统以理解层为中枢构成星型拓扑，新增感知或反馈模块也只需以相同协议的TCP客户端接入，无需修改系统的核心逻辑。



\subsection{自定义TCP通信协议设计}

在协议格式的设计过程中，本系统经历了从二进制协议到JSON文本协议的演进历程。

\textbf{（1）二进制协议方案}：早期设计采用长度前缀结合消息类型的二进制协议格式，具体结构为：4字节大端序无符号整数表示载荷长度，1字节无符号整数表示消息类型（\texttt{0x00=TEXT}、\texttt{0x01=IMAGE}、\texttt{0x02=COMMAND}、\texttt{0x03=REGISTER}），其后为载荷数据。该方案在理论上具有最高的解析效率，但在实际开发中暴露出两个问题：其一，图片数据与文本数据采用完全不同的编码路径，处理混合类型消息时需要额外的类型判断与解码逻辑，增加了开发复杂度；其二，二进制格式无法在开发阶段直接阅读，调试与问题定位均较为困难。

\textbf{（2）JSON文本协议方案}：基于上述实践经验，本系统最终采用“4字节大端序长度前缀 + UTF-8编码JSON载荷”的协议格式。发送端将JSON对象序列化为UTF-8字节序列，计算其长度并以大端序写入前4字节，随后写入载荷；接收端据此解析，确保TCP流式传输中消息边界的正确划分。该协议将所有数据统一封装为JSON对象，核心字段定义如下：

\begin{itemize}
\item \texttt{type}：消息类型，取值为 \texttt{text}（普通文本消息）、\texttt{image}（Base64编码的图片数据）、\texttt{command}（控制命令）、\texttt{register}（客户端注册）
\item \texttt{data}：载荷内容——文本消息时为UTF-8字符串，图片消息时为Base64编码的二进制数据，command类型时为具体命令名称
\item \texttt{client\_type}：发送者身份标识，取值包括 \texttt{unity}、\texttt{mediapipe}、\texttt{raspberry\_pi}、\texttt{debug} 四种。客户端在注册时通过此字段声明自身类别，服务端据此维护已连接客户端的注册表
\item \texttt{request\_id}：请求追踪标识，采用UUID格式。当命令需要响应时，发起方携带此字段，响应方须原样回传以关联请求—响应对
\item \texttt{relay\_to}：直接转发标识。若消息中包含此字段，服务端不再将消息投入智能体队列，而是直接转发至目标客户端，实现低延迟的客户端间直连通信
\end{itemize}

其中，\texttt{register}类型具有特定的语义约定：该类型仅由客户端向服务端发起。当客户端首次连接到服务端时，须发送一条\texttt{register}类型消息并携带\texttt{client\_type}字段标识自身类别。服务端在收到注册消息后记录该连接的身份信息，后续该连接发送的消息无需重复携带\texttt{client\_type}，服务端将自动补充发送者身份。

JSON文本协议具有三方面优势：文本形式便于开发阶段的调试与日志分析；统一的数据封装方式简化了协议解析逻辑；Base64编码虽然增加了约33\%的数据体积，但换取了协议的一致性与可维护性。考虑到本系统运行于本机与局域网环境下，网络带宽充足且延迟极低（通常低于5ms），上述开销在实际使用中完全可接受。表\ref{tbl:protocol-examples}按消息类型给出了四种典型场景下的协议使用实例。

\subsection{功能模块设计}
\label{sec:module-design}

以上述三层架构为框架，系统划分为四个核心功能模块：EchoAgent智能体模块、MediaPipe感知模块、Unity客户端模块与树莓派灯光控制模块，另有一个TCP服务端模块承担通信中枢职责。各模块具有明确的职责边界、内部结构与对外接口，其所依赖的关键技术蕴含在模块内部设计之中。本节依次阐述各模块的设计要点。


\subsubsection{EchoAgent智能体和TCP服务端模块}

TCP服务端与EchoAgent运行于同一进程，也是统一设计的。

首先，服务端在固定端口上监听连接，每个客户端首次连接时须发送注册消息声明自身类别（unity、mediapipe、raspberry\_pi或debug四种），服务端据此将连接与身份绑定并维护已注册客户端表，后续消息发送时按类型匹配目标连接，无需每条消息携带身份标识。

标记为直转（relay\_to）的消息不经智能体队列，由服务端直接转发至目标客户端，实现毫秒级的客户端间直连——典型场景为MediaPipe将指向方向数据中继至Unity驱动角色移动，要求端到端延迟在100ms以内；普通消息则写入消息队列，交由EchoAgent处理。这一双通路设计在延迟敏感的实时控制与需要语义理解的高层决策之间取得了平衡。在拓扑结构上，所有客户端均以TCP Client身份接入服务端，彼此不直接建立连接，新增感知通道或反馈设备仅需实现协议即可接入，无需修改核心逻辑，保证了系统的可扩展性。

EchoAgent是理解层的认知核心，从共享消息队列中批量获取多源感知数据，经大语言模型综合推理后，自主选择并调用工具函数生成控制决策。

EchoAgent与EchoServer及消息队列的集成方式如图\ref{fig:agent-server-topology}所示：EchoServer在端口65432上持续监听TCP连接，将非注册、非中继类消息写入共享的\texttt{asyncio.Queue}；EchoAgent按固定间隔从队列中批量取出消息，交由大语言模型推理后自主调用工具。服务端与Agent各自在独立的异步循环中运行，以生产者—消费者模式协同消息接收与决策处理。

智能体的完整交互闭环如图\ref{fig:agent-trace}所示：MediaPipe模块检测到参展者的手势或表情变化后，通过TCP上报至智能体；智能体结合当前叙事章节、参展者进度与情绪上下文进行综合决策，必要时调用截图工具获取Unity当前画面以辅助判断；截图请求经TCP发送至Unity客户端，Unity执行截图后将图像回传；智能体理解图像内容后发起下一步交互指令，形成"感知—理解—反馈"闭环。

\begin{figure}[htbp]
  \centering
  \includegraphics[width=1.0\textwidth]{pic/智能体决策完整流程时序图.pdf}
  \caption{智能体决策流程时序图}
  \label{fig:agent-trace}
\end{figure}

EchoAgent通过LangChain的\texttt{@tool}装饰器定义了五个工具函数，覆盖从设备控制到多模态输出的完整能力集。各工具均以EchoAgent的静态方法形式实现，在初始化时通过闭包绑定EchoServer实例，工具参数均采用简单字符串类型：

\begin{enumerate}
\item \textbf{\texttt{send\_to\_client}}：向指定类型的客户端发送通用消息。参数为\texttt{client\_type}（\texttt{unity}、\texttt{mediapipe}或\texttt{raspberry\_pi}）与\texttt{message}（纯文本）。内部通过EchoServer遍历已注册连接，找到匹配类型的客户端后发送JSON消息。

\item \textbf{\texttt{request\_unity\_screenshot}}：请求Unity客户端截取当前画面并回传。无参数，内部向Unity客户端发送\texttt{request:screenshot}指令，Unity端执行截图后以Base64编码的JPEG图像回传至智能体，智能体在下一轮轮询中将其作为多模态上下文的一部分进行分析。

\item \textbf{\texttt{control\_lights}}：控制实体LED灯阵。参数为\texttt{mode}（灯光模式：\texttt{chase}循环点亮、\texttt{solid}实色、\texttt{rainbow}彩虹渐变、\texttt{breathing}呼吸，以及\texttt{gain\_note}/\texttt{play\_note}音符联动反馈）、\texttt{color}（\texttt{solid}模式的颜色，如\texttt{warm\_amber}、\texttt{cool\_blue}等）与\texttt{note}（音符反馈模式下的音符名称：\texttt{waterdrop}、\texttt{crossing}、\texttt{tide}、\texttt{breeze}）。内部构造\texttt{lights:mode[:color][:note]}格式指令，经TCP发送至树莓派。

\item \textbf{\texttt{play\_music}}：控制交互应用中的音乐与音频播放。参数\texttt{action}为\texttt{"类别:操作"}格式字符串——演奏音符（\texttt{play\_note:waterdrop}等）或切换情绪背景音乐（\texttt{set\_mood:calm/tense/warm}）。内部封装为\texttt{music:action}指令发送至Unity。

\item \textbf{\texttt{speak}}：通过MiniMax TTS服务将文本转为语音并播放。参数\texttt{text}为待朗读文本。内部调用MiniMax\texttt{speech-2.8-turbo}模型，使用Mandarin Warm Girl音色生成MP3音频并播放。
\end{enumerate}

智能体的行动能力由五个工具函数定义，覆盖系统全部执行端。send\_to\_client向指定客户端发送通用消息，request\_unity\_screenshot主动获取Unity当前画面以辅助视觉理解，control\_lights驱动实体LED灯阵的模式与色彩切换，play\_music控制交互应用中的音乐播放与情绪切换，speak通过TTS服务将文本转为语音。各工具在初始化时绑定通信层实例，使智能体在推理过程中可直接操作各执行端。

在消息处理方面，感知层各模块的上报消息到达时机不可预测，而大语言模型的推理延迟在秒级，因此模块采用生产者—消费者模式解耦输入与决策：服务端将需处理的消息写入共享消息队列，EchoAgent以固定间隔从队列中一次性取出所有积压消息，批量送入模型推理。这一设计将多源异步到达的消息聚合后统一推理，使智能体能够在同一上下文中综合考虑手势、表情与场景事件的关联，避免碎片化的逐条响应。在提示词层面，系统提示词向模型传递三个层次的信息：交互应用定位（《回声之境》的叙事主题、章节结构与情感目标），客户端角色定义（Unity、MediaPipe、Raspberry Pi三类客户端的身份与能力），以及调试模式指引（如智能体在收到Unity注册消息后主动请求截图以建立场景认知）。提示词是连接交互应用叙事设计与智能体决策行为的关键桥梁，其措辞直接影响工具选择的准确性与回复风格的自然度。

\subsubsection{MediaPipe感知模块}

MediaPipe模块居于感知层，运行于独立进程中，负责实时捕获参展者的手势与面部表情信息。

在手势识别方面，模块利用MediaPipe内置手势分类器识别Open\_Palm、Pointing\_Up、Victory等预定义手势类别。在内置分类器之上，模块叠加了三层自定义检测逻辑：手势变化检测层通过缓存比对实现变更触发上报，避免同一手势持续期间的冗余网络流量；食指指向方向检测层从手部关键点坐标直接计算方向向量，完全独立于内置分类器，为角色移动提供连续的二维方向输入；双手挥散检测层通过双腕距离阈值判定Open\_Palm姿态下的挥散动作，配有冷却时间防止重复触发。三层检测的输出通道各不相同——手势变化事件上报至EchoAgent供高层决策，指向方向经中继通道直发Unity以保证跟手性，挥散动作触发展览开场动画。

在面部识别方面，模块通过MediaPipe FaceLandmarker输出52维面部形变系数。为避免逐帧全量上报带来的网络与处理开销，模块设计了双重节流机制：仅保留置信度高于阈值的形变系数以滤除噪声，同时计算当前帧所有活跃系数的均值，仅当变化幅度超过设定阈值且距上次上报超过最小间隔时才推送。效果是面无表情时几乎不产生推送，表情丰富时约每秒2次，在信息完整性与资源开销之间取得平衡。

在多线程调度方面，模块内部三条线程协同工作：主线程负责预览窗口渲染，摄像机线程以高帧率读取摄像头帧并分发给两个识别器，网络事件循环线程承载全部网络收发。跨线程桥接的关键在于将识别回调线程中产生的发送请求安全调度至网络线程，避免并发操作网络连接。

\subsubsection{Unity客户端模块}

Unity客户端模块同时跨越感知层与反馈层，是系统交互体验的直接载体。模块以GameRoot单例为枢纽，通过五个子模块协同完成通信、输入映射、状态编排、视觉生成与相机控制等功能。

AgentCommunicator承担Unity端的TCP客户端角色，确保发送侧串行化以避免数据交错，同时将接收回调投递至Unity主线程以符合其单线程执行模型；还负责响应EchoAgent的截图请求——在帧末尾截取当前画面并以图像格式回传。VirtualAgentDevice向Unity输入系统注册为独立输入设备，提供二维摇杆与按钮控制元；来自网络的移动指令经解析后注入输入管线，使远程手势与本地键盘、手柄共享同一套控制逻辑，无需在角色控制器中编写网络输入分支；模块同时内置移动超时检测，若超过设定时长无新指令则自动清零移动向量，防止指令粘滞。GameStateManager作为交互流程的编排中枢，维护章节状态、输入管控与事件订阅，通过输入映射的分级禁用实现标题阶段屏蔽角色移动但保留界面响应的精细控制，在初始化阶段集中完成事件订阅与状态变更链路绑定，使状态变迁的全流程可在一处追踪。

在视觉生成方面，模块基于Shader Graph构建非真实感渲染着色器，暴露抖动速度、抖动强度、菲涅尔颜色等Uniform参数，供EchoAgent通过控制指令动态调整。着色器利用菲涅尔效应、顶点噪声偏移与GPU Instancing等技术，在维持交互帧率的前提下实现半透明抖动山峦、风格化草地摆动与体积雾等动态视觉效果。视觉参数可随情绪状态变化而调整——例如低强度冷色调对应迷茫氛围，暖色调对应锚定氛围——使画面风格与情感叙事同步演进。在相机控制方面，模块基于State Driven Camera机制，将交互流程中的不同阶段映射为Idle、Following、TopShowing、Showing四种虚拟相机机位；机位切换由动画状态机驱动，其中Following机位沿预设样条曲线运动并保持注视目标，实现影视化的镜头调度。

\subsubsection{树莓派灯光控制模块}

树莓派模块居于反馈层，负责将智能体的灯光决策转化为实体空间的光影变化。模块运行于树莓派5之上，通过GPIO引脚输出控制信号，驱动64颗WS2812可编程RGB LED灯珠；灯珠沿四个音符图标外轮廓物理排布，各音符对应一段连续灯珠区间，由音符—灯珠索引映射表维护对应关系。

模块支持两类灯光模式。基础模式中，追逐（chase）效果使光点循环移动，利用视觉暂留形成流动观感；呼吸（breathing）效果以三角波函数驱动全带灯珠同步明暗起伏；彩虹追逐（rainbow）效果维护多个色相各异的光点，各自拖曳渐暗拖尾，色相缓慢旋转产生流动的彩虹效果。色彩控制采用HLS颜色空间，将色相与亮度解耦，使色彩渐变逻辑的表达更为自然。音符联动模式直接根据音符—灯珠索引映射定位对应灯珠：gain\_note点亮目标区间，play\_note在点亮基础上叠加短暂闪烁序列，形成与虚拟场景中音符演奏同步的视觉伴随反馈。动态模式运行于独立线程，每次切换模式时先终止上一线程再启动新效果，保证模式切换即时响应且不阻塞指令接收。

以下各节依次详述上述模块所依赖的通信协议、控制命令体系与实体展览环境的具体设计。

\subsection{控制命令设计}

基于上述协议格式，系统定义了一套控制命令用于各模块间的协调交互。表\ref{tbl:command-table}按接收客户端分组，汇总了全部控制命令的发起方、接收方与使用说明。

命令的命名遵循三级约定，以前缀区分语义类别：

\begin{enumerate}
\item \textbf{\texttt{request:}前缀}：请求型命令，期望接收方处理后返回响应。发起方须携带\texttt{request\_id}字段，接收方响应时原样回传以关联请求。典型实例为\texttt{request:screenshot}——智能体请求Unity或MediaPipe客户端截取当前画面以查看运行状态。
\item \textbf{\texttt{input:}前缀}：输入注入型命令，用于向目标客户端模拟用户交互事件。典型实例包括\texttt{input:submit}（触发提交事件）、\texttt{input:move}（将食指指向映射为输入坐标）、\texttt{input:cancel}（取消当前输入）和\texttt{input:navigate}（触发导航操作）。
\item \textbf{无前缀}：直接控制命令，即发即忘，无需响应。此类命令主要用于设备控制与状态同步，如灯光模式切换（\texttt{chase}、\texttt{solid}、\texttt{rainbow}、\texttt{breathing}）、音符事件的灯光伴随反馈（\texttt{gain\_note}、\texttt{drop\_note}、\texttt{play\_note}），以及配置开关（\texttt{hand\_direction}）。
\end{enumerate}

\subsection{实体展览环境设计}

实体装置旨在将虚拟世界的交互状态延伸至物理空间，增强观展者的沉浸感与具身参与体验。

\textbf{技能图标实体化}：将交互应用中的四个音符图标实体化，使用松木板制作展览实物。图标图案采用矢量绘图工具Affinity绘制贝塞尔曲线构建流畅的音符轮廓线条粘贴至木板上，配合装饰性麻绳串联固定于展台。实体图标与交互应用内的点亮状态保持同步，当参展者在交互应用中演奏音符时，对应图标同步亮起LED灯效。

\textbf{灯光控制系统}：灯条采用WS2812可编程RGB LED灯带，具有单点可控、色彩丰富、响应速度快的特点。灯带由树莓派通过PWM（脉冲宽度调制）信号控制，树莓派作为TCP Client连接至智能体服务端，接收来自智能体的灯光控制指令，改变颜色、亮度和闪烁模式，实时驱动灯带产生与虚拟场景同步的动态光影效果。

\textbf{信号传递流程}：实体装置的信号链路为：MediaPipe/Unity感知模块 → TCP上报 → 智能体决策 → TCP下发控制指令 → 树莓派PWM驱动LED。树莓派接收到控制指令后，通过Python的rpi-ws281x库将PWM信号转换为LED灯带的显示效果，实现从虚拟场景到实体空间的跨媒介联动。

\subsection{立题立意}

《回声之境》以叙事性交互为核心特征，伴随参展者情绪变化与章节推进，在不同阶段营造差异化的场景情绪基调。各场景内，旅人的音符音色、音阶与背景音乐的调式保持和声协调，力求营造富有诗意的沉浸式参观体验。

叙事结构与手法方面，《回声之境》以旅人的旅程为叙事主线，隐喻个体从自我迷茫走向全然自由的成长历程，围绕自我认知、人际边界与知识接纳三层命题展开。交互应用依此设置三个章节——初域·未定之原、聚落群·彼方的光影之城、深流之径·未被触及的知识海——三者在情感基调与交互机制上层层递进。

\subsubsection*{第一章：初域·未定之原——自我迷茫与锚定}

本章对应情感状态从“迷茫”到“锚定”的转换，核心目标是引导参展者解锁水滴音符，学会在未定中锚定自我。设计理念借鉴《最后的篝火》的温柔引导机制，全程无惩罚，通过渐进式教学使参展者理解音符塑造世界的核心逻辑。

远景山峦在本章中承担视觉引导与情感暗示的双重职责。半透明、边缘模糊的山峦形态隐喻旅人尚未明晰的方向感——山体的不稳定抖动象征内心的徘徊与探寻；当山峦被音符固化后逐渐变得坚实，则对应旅人在迷茫中逐步锚定自我、找到方向的过程。视觉层面的虚实转换与情感层面的迷茫-锚定转变形成对照，使参展者在潜意识层面感受情绪叙事的递进。

关卡流程依循四个递进阶段展开：参展者首先从迷雾中显现，面对半透明流动的山峦与旷野，在旁白引导下尝试与世界互动；随后在引导下奏响水滴音符，山峦短暂抖动后恢复流动，参展者需持续奏响以完成固化；继而进入三个方向锚点谜题——“落定的石阶”（过去的锚点）要求参展者观察漂浮石块的流动规律并在恰当时机固化，“无风的山谷”（当下的锚点）需依次固化乱流核心以平息环境扰动，“迷雾的边界”（未来的锚点）则要求参展者自主判断固化的位置与方向，独立开辟道路。三个锚点全部激活后，迷雾散去，未定之原固化为稳定地貌，一条宽阔光路延伸向下一章节。

本章多模态交互涵盖四个维度：持续捏合手势映射为持续奏响音符；发声音量控制固化范围；山体从半透明流动态渐变为坚实青翠形态；水滴音符从单音发展为完整旋律短句。

\subsubsection*{状态驱动与相机编排设计}

《回声之境》作为一款交互应用，与电子游戏的区别在于它更注重叙事时的演出表现。因此，为了实现在前文中所描述的章节叙事，我们需要有一套明确的状态路径表。在相机设置上，它也会与电子游戏有所差别。基于其特殊的交互事件和演出需求，本作品没有使用常见的第三人称自由视角转动、也并非完全的固定俯视角跟随，而是更类似于影视拍摄时的分镜脚本，采用了多机位切换与轨道控制来编排了一种状态驱动的相机控制方式。

\subsubsection*{第二章：聚落群·彼方的光影之城——关系探索与边界}

本章对应情感状态从“碰撞”到“边界”的转换，核心目标是解锁道路交错音符，使参展者学会在关系中保持自我边界。设计理念参考《最后的篝火》“中心枢纽+多分支故事线”结构，四个分支区域各自对应一段社交与情感的隐喻。

旅人进入城市时，嘈杂人声导致街道挤压变窄，尝试以水滴音符应对无效——系统由此暗示旧规则在此失效，需要习得新的交互能力。关卡设置四个分支区域：“回声交汇所”中，参展者帮助影子旅者连接断裂的光路，通过动作同步建立共鸣后用水滴音符连接彼此道路；“情绪风塔”中，参展者逐层应对欢喜、悲伤、愤怒、恐惧四种情绪，在共情与自我保护之间寻找平衡；“镜影回廊”中，参展者在布满镜面的空间里忽略扭曲的影像评价，锚定真实的自我；“离别的岔路口”中，参展者帮助影子旅者理解离别并非终结，各自走向属于自己的方向。集齐四个分支的碎片后，城市建筑停止挤压变形，旅人脚下的道路恢复宽阔平稳。

本章引入三项核心交互机制：情绪折射——建筑形态随旅人情绪强度变化，情绪平静时建筑舒展，波动时则扭曲挤压；共鸣系统——与影子旅者的动作同步率达到阈值后触发共鸣效果；边界保护——道路交错音符可在参展者周围划定视觉化的自我边界，过滤外界情绪的干扰。

\subsubsection*{第三章：深流之径·未被触及的知识海——知识接纳与自由}

本章对应情感状态从“敬畏”到“驾驭”再到“自由”的多阶段转换，核心目标是依次解锁海浪音符与风音符，使参展者获得完全的表达自由。设计理念围绕“学得越多，未知越多”的核心命题展开，通过知识潮机制实现渐进式挑战。

关卡分为浅滩区与深潮区两个阶段。浅滩区引入知识潮机制：参展者每获取一个知识碎片（依次对应观察、耐心、试错、联结、放下、接纳六项学习特质），潮水便上涨一层，可立足的礁石减少，但深渊中的光点更加明亮密集。集齐六个碎片后解锁海浪音符，参展者由此学会在知识的潮水中保持稳定。深潮区设置三道情感浪潮，分别对应迷茫、遗憾、无知三种成长困境，旅人需运用已解锁的音符逐一化解。触碰海心之核后，四个音符的旋律汇聚为一首完整的乐曲，风音符随之解锁——参展者由此获得完全的表达自由。值得提及的是，开篇的晴天娃娃在深潮区回归，旅人由此明白它从未抛下自己，只是在前方等待，在叙事层面形成伏笔回收。

完成深潮区挑战后，系统进入自由探索阶段：参展者可自由奏响四个音符，每个音符均会改变整个世界的视觉形态，实现无限的个性化探索。该阶段使参展者充分体验“学以致用”的成就感与“随心所欲不逾矩”的自由状态。

三章的叙事线索层层递进：第一章聚焦自我认知，未定之原是对自我迷茫的具象化；第二章聚焦关系探索，光影之城是对人际边界的具象化；第三章聚焦世界接纳，深流之径是对知识与未知态度的具象化。四个音符作为锚定自我、连接他人、驾驭未知、通达自由的四重能力象征，共同构成了旅人从迷茫走向自由的完整成长弧线。

\subsubsection{交互设计到系统模块的映射}

上述交互场景与关卡流程并非悬浮于技术框架之上的纯概念设计，而是与第\ref{sec:module-design}节所述各功能模块形成了明确的支撑关系。本节以三章为线索，梳理交互设计元素到系统框架模块的映射，以阐明叙事体验是如何经由各模块的协同工作而落地的。

第一章的核心交互——手势指向移动——在系统层面由MediaPipe手势识别子模块、TCP中继通道与Unity VirtualAgentDevice输入子模块三者串联实现：食指指向方向经三层检测逻辑提取后，以\texttt{input:move}指令中继至Unity，注入Input System管线驱动旅人沿指向方向行走，端到端延迟控制在100ms以内。标题消散由双手挥散检测（MediaPipe端）经AgentCommunicator校验面部在场后触发EchoTitle动画，涉及MediaPipe手势与面部两个子模块、TCP服务端中继机制及Unity GameStateManager的状态编排。山峦的半透明抖动与固化视觉效果由Unity动态视觉生成子模块承担——着色器的菲涅尔边缘光与顶点噪声偏移参数随情绪状态变化而调整，固化过程的视觉过渡由GameStateManager的状态变迁事件触发。

第二章的核心交互——情绪折射与共鸣——在系统层面由MediaPipe面部识别子模块与EchoAgent智能体模块协同完成。面部形变系数经双重节流后上报至智能体，EchoAgent结合叙事上下文进行情绪语义推理，判定参展者当前的情绪强度与倾向后，通过\texttt{send\_to\_client}工具向Unity下发视觉参数调整指令，驱动建筑形态的舒展与扭曲。共鸣系统的动作同步率检测由MediaPipe手势识别子模块承担，同步达标后EchoAgent调用\texttt{play\_music}工具触发音乐反馈，同时通过\texttt{control\_lights}工具驱动树莓派灯光控制模块切换灯光氛围。边界保护机制则依赖MusicNoteController协调音符状态，并通过AgentCommunicator同步通知树莓派端触发相应灯光效果。

第三章的核心交互——知识潮渐进与自由探索——在系统层面涉及最完整的模块链。知识碎片的收集进度由Unity GameStateManager追踪，潮水上涨的视觉变化由动态视觉生成子模块执行；海浪音符解锁后，EchoAgent的\texttt{control\_lights}与\texttt{play\_music}工具同时驱动灯光模式切换与音乐变奏；自由探索阶段四个音符的演奏分别触发对应的视觉形态变化（Shader Uniform参数调整）、音效反馈（音乐播放控制工具）与实体灯光伴随效果（树莓派灯光控制模块的\texttt{gain\_note}/\texttt{play\_note}联动），虚拟画面与物理光影在同一指令下保持严格同步，形成虚实联动的完整交互闭环。

综上所述，三章的交互设计既各自侧重不同的模块组合，又共用同一套“感知—理解—反馈”架构：MediaPipe模块持续承担手势与表情的感知角色，EchoAgent模块负责跨模态理解与决策，Unity模块输出虚拟视觉与音效反馈，树莓派模块将变化延伸至实体空间。这种设计使叙事内容与系统框架之间形成了相互支撑而非彼此独立的关系。

\subsection{音乐交互设计}

从应用名称《回声之境》可以看出，本设计的初衷是构建一个音乐驱动的互动体验。在新建项目时，我在项目简介里写下了这样的描述——\textit{an experimental interactive application where sound shapes the world}。基于整体应用的叙事特性，各场景绑定特定的配乐调式与速度标识：不同场景运用不同调式与曲速的背景音乐，旅人演奏的音符若不在当前调式上会造成和声冲突。因此，每个场景均预设固有的调式标识，该设计参考了游戏《Songbird Symphony》中的音乐交互机制。

如表\ref{tbl:note-design}所示，旅人在旅程中可依次获得水滴、道路交错、海浪和风这四个音符，通过指引依次获得。音符不仅是演奏与视觉反馈的载体，更是旅人理解世界、塑造世界的方式。每个音符承载着隐喻性的象征意义，其演奏效果对应精神层面的某种能力。

其中音符的音级分别为一级、五级、二级和六级。这四个音级的设计思路来自于乐理中的五度圈。五度圈是乐理中描述十二个音之间五度关系的圆形图示：从任一音出发，顺时针方向每次上行纯五度，逆时针方向每次下行纯五度。在五度圈上，I—V—II—VI这四级恰好构成顺时针方向上的连续四步——从主音（I）出发，上行五度至属音（V），再上行五度至上主音（II），再上行五度至下中音（VI），如图\ref{fig:circle-of-fifths}所示。

\section{交互系统框架实现}

\subsection{TCP通信与并发控制}

\subsubsection{长度前缀JSON协议}

系统各模块间通过统一的二进制帧协议进行通信：每帧由 4 字节大端序无符号整数（表示负载长度）与紧随其后的 UTF-8 编码 JSON 负载组成。接收方先读取 4 字节长度前缀，再按长度读取完整 JSON 数据，以此实现帧边界划分。JSON 消息体包含以下字段：\texttt{type}（消息类型，可选 \texttt{text}、\texttt{image}、\texttt{command}、\texttt{register}）、\texttt{data}（负载内容）、\texttt{client\_type}（发送方身份标识，注册消息使用）、\texttt{request\_id}（UUID 格式请求标识，用于关联请求与响应）及 \texttt{relay\_to}（中继目标，指定消息经服务器直接转发至某类客户端）。客户端类型包括 \texttt{mediapipe}、\texttt{unity}、\texttt{raspberry\_pi} 与 \texttt{debug}，覆盖系统全部通信节点。其 TypedDict 结构定义如代码\ref{code:json-message}所示。

\begin{code}
\caption{JsonMessage 消息结构定义}
\label{code:json-message}
\begin{codebox}
class JsonMessage(TypedDict):
    ""用于存储JSON消息的字典类""
    type: str # text | image | command | register
    data: str # 文本内容或base64编码数据，command 时为命令内容
    client_type: NotRequired[ClientType] # 发送这个消息的客户端类型：mediapipe | unity | raspberry_pi | debug
    request_id: NotRequired[str] # 需要回应的响应时必须，否则非必须
    relay_to: NotRequired[str] # 直接转发 如果含本字段 则此消息直接转发给目标客户端
\end{codebox}
\end{code}

\subsubsection{EchoServer与客户端管理}

TCP 服务端由 EchoServer 类实现，基于 Python \texttt{asyncio} 在端口 65432 上监听连接。每个客户端连接对应一个 LengthPrefixProtocol 实例，维护独立的接收缓冲区与长度解析状态机。客户端首次连接时须发送注册消息（\texttt{\{"type": "register", "client\_type": "..."\}}），服务端据此将连接与其身份类型绑定，后续的 \texttt{send\_message} 操作遍历已注册连接集合，按类型匹配目标客户端。

协议层支持中继转发机制：若消息含非空 \texttt{relay\_to} 字段，服务端直接将消息转发至匹配类型的所有对等连接，不经消息队列，以此实现客户端间的低延迟直通——典型场景为 MediaPipe 将指向方向数据中继至 Unity 驱动角色移动。不含 \texttt{relay\_to} 的普通消息则写入共享的 \texttt{asyncio.Queue}，交 EchoAgent 处理。

\subsubsection{Python端TcpClient实现}

服务端负责消息的汇总与路由，而各感知模块则通过统一的TCP客户端接入系统。TcpClient 是客户端侧的协议实现，其中Python实现基于asyncio 异步IO，封装了长度前缀帧协议的编解码逻辑，并提供了订阅/退订式的事件回调机制——调用方可按消息类型（text、image、command）分别注册处理函数，当对应类型消息到达时自动分派。

TcpClient内部维护一个 \texttt{\_Event} 辅助类，管理回调函数的添加（+=）、移除（-=）与分发。消息接收循环 \texttt{\_receive\_loop} 以异步任务形式运行：先读取4字节长度前缀（\texttt{struct.unpack(">I", ...)}，> 表示大端序），再按长度读取JSON负载，解码后根据type字段分派至对应的 \texttt{\_Event} 实例（\texttt{on\_text}、\texttt{on\_image}、\texttt{on\_command}）。发送侧统一通过 \texttt{\_send\_json} 方法完成长度前缀编码与JSON序列化，对外暴露 \texttt{send\_text}、\texttt{send\_image}、\texttt{send\_register} 与 \texttt{send\_command} 四个高层接口。核心实现如代码\ref{code:tcp-client}所示，因篇幅原因此处代码已做大幅简化。

\begin{code}
\caption{简化的TcpClient 客户端核心代码}
\label{code:tcp-client}
\lstset{style=codeblock}
\begin{lstlisting}
# 事件分发：订阅/退订 + 回调派发
class _Event:
    def __init__(self, name):
        self._callbacks = []

    def __iadd__(self, callback):
        self._callbacks.append(callback)
        return self

    def __isub__(self, callback):
        self._callbacks.remove(callback)
        return self

    def dispatch(self, *args, **kwargs):
        for cb in self._callbacks:
            try:
                cb(*args, **kwargs)
            except Exception:
                logger.exception(f"Error in {self._name} handler")

# 长度前缀帧接收 + 类型分派（含自动重连）
async def _receive_loop(self):
    try:
        while self._reader:
            length_prefix = await self._reader.readexactly(4)
            payload_len = struct.unpack(">I", length_prefix)[0]
            json_data = await self._reader.readexactly(payload_len)
            msg = json.loads(json_data.decode("utf-8"))
            {
                "text":    lambda: self.on_text.dispatch(msg["data"]),
                "image":   lambda: self.on_image.dispatch(
                                 base64.b64decode(msg["data"])),
                "command": lambda: self.on_command.dispatch(msg),
            }.get(msg["type"], lambda: None)()
    except asyncio.IncompleteReadError:
        logger.info("Connection closed by peer")
    except ConnectionResetError:
        logger.warning("Connection reset")
    finally:
        await self._cleanup_transport()
        if self._should_reconnect:
            await asyncio.sleep(self._reconnect_delay)
            self._reconnect_delay = min(self._reconnect_delay * 2, 30.0)
            asyncio.create_task(self.connect())

# 长度前缀帧发送
def _send_json(self, obj):
    raw = json.dumps(obj, ensure_ascii=False).encode("utf-8")
    self._writer.write(struct.pack(">I", len(raw)) + raw)
\end{lstlisting}
\end{code}

除上述基本收发逻辑外，TcpClient 还内置了自动重连机制：当连接因对端关闭或网络异常而断开时，接收循环在清理当前传输层后不会直接退出，而是按指数退避策略（初始 1s，每次翻倍直至上限 30s）延迟后自动发起重连。重连成功后触发 \texttt{on\_connected} 事件，调用方可借此实现自动重新注册等恢复逻辑。该机制使 MediaPipe 感知模块在服务端重启后无需人工干预即可恢复通信。


\subsection{智能体EchoAgent实现}

\subsubsection{运行机制}

EchoAgent 是本系统的理解层中枢，基于 Qwen3.6\citing{qwen36plus} 构建，负责整合多源感知数据并做出交互决策。系统启动时按以下顺序初始化各组件：首先创建一个全局的异步消息队列（\texttt{asyncio.Queue}），随后创建 EchoServer 并注入队列引用，最后创建 EchoAgent 实例，使其同时持有队列与 EchoServer 的引用。EchoAgent 与 EchoServer 及消息队列的集成方式如图\ref{fig:agent-server-topology}所示。

智能体的完整交互闭环已在系统总体设计中详述，此处不再重复。

\subsubsection{Deep Agents 框架集成}

本系统的智能体基于 Deep Agents 框架构建。Deep Agents 是一个基于 LangGraph 与 LangChain 的智能体框架，通过 \texttt{create\_deep\_agent()} 工厂函数创建编译后的状态图（\texttt{CompiledStateGraph}），提供内置的任务规划、上下文管理与子代理委派能力。智能体 使用 \texttt{InMemorySaver} 作为对话检查点存储器，维持跨轮次推理的状态连续性。

在模型接入方面，框架通过 LangChain 的标准 Chat Model 接口与底层大语言模型交互，支持灵活切换模型提供商。系统的系统提示词（System Prompt）通过结构化自然语言向模型传递《回声之境》的交互应用定位、三类客户端角色（Unity、MediaPipe、Raspberry Pi）、消息类型体系（文本与图像），以及关键的调试模式指引——智能体 在收到 Unity 注册消息后主动请求截图以建立场景认知。

\subsubsection{批量消息处理与决策流程}

EchoAgent 的决策循环以轮询模式运行：每 5 秒从消息队列中一次性排空所有积压消息，将其转换为 LangChain 的 \texttt{HumanMessage} 列表后批量送入 智能体。对于文本类消息，直接将原始 JSON 字符串作为消息内容；对于图像类消息，则构造包含 Base64 编码图像与描述文本的多模态内容结构。智能体 通过 \texttt{deep\_agent.ainvoke()} 执行推理，模型根据系统提示词与当前上下文自主决定是否以及调用哪个工具，工具执行结果以 \texttt{ToolMessage} 形式追加至对话历史，供下一轮推理使用。

这种批量处理模式的设计兼顾了两方面考量：一方面，将多源异步到达的消息聚合后统一推理，使 智能体 能够在同一上下文中综合考虑手势、表情与场景事件的关联；另一方面，5 秒的间隔避免了模型 API 的频繁调用，在交互响应性与资源开销之间取得了平衡。

\subsubsection{手势识别与指向检测}

手部感知由 HandsRecognizer 类实现，基于 MediaPipe GestureRecognizer 模型（\texttt{gesture\_recognizer.task}）运行于 LIVE\_STREAM 模式。MediaPipe 内置手势分类器可识别 \texttt{Open\_Palm}、\texttt{Pointing\_Up}、\texttt{Victory}、\texttt{Thumb\_Up} 等预定义手势类别，每帧检测结果包含手势标签、置信度与 21 个手部关键点的归一化坐标。

然而，MediaPipe 的内置手势输出并不能直接满足系统的交互需求。在本设计中，还引入了食指指向来控制旅人移动。为此，HandsRecognizer 在 MediaPipe 回调之上叠加了三层检测逻辑，各自遵循不同的触发策略。

\textbf{手势变化检测}。手势类别数据若逐帧上报，将在同一手势持续期间产生大量冗余 TCP 流量。HandsRecognizer 内部维护一个以手部索引为键的字典 \texttt{\_current\_gestures}，缓存每只手上一次的手势类别名。每帧 MediaPipe 结果到达后，逐一比对当前手势与缓存值，仅当任一手指的手势类别发生变化时才触发结果回调，如代码\ref{code:gesture-change}所示。

\begin{code}
\caption{手势变化检测：缓存比对，仅变更时触发}
\label{code:gesture-change}
\lstset{style=codeblock}
\begin{lstlisting}
changed = False
for hand_index, hand_landmarks in enumerate(result.hand_landmarks):
    gesture = result.gestures[hand_index][0].category_name if result.gestures else ""
    if self._current_gestures.get(hand_index, "") != gesture:
        self._current_gestures[hand_index] = gesture
        changed = True
if changed:
    for callback in self._result_callbacks:
        callback(hand_result)
\end{lstlisting}
\end{code}

这一设计使手势数据的网络上报频率与参展者的手势变化节奏一致——维持同一手势时零流量，切换手势时即时响应。

\textbf{食指指向方向检测}。该算法完全独立于 MediaPipe 的内置分类器，直接从手部关键点坐标计算方向向量。首先进行手部选择：若画面中仅检测到一只手则直接选用，若检测到两只手则按 MediaPipe 的 handedness 分类优先选取左手，以契合多数参展者惯用右手进行操作、左手负责指向的自然姿态。随后判定食指是否伸直——计算食指尖（landmark 8）至食指掌骨基部 MCP 关节（landmark 5）的归一化欧氏距离，超过阈值 0.07 即视为伸直态；这一阈值基于经验设定，可过滤掉手指微弯或握拳状态下的误触发。最后计算方向向量：将归一化坐标乘以当前帧的实际像素尺寸（该尺寸从每次 \texttt{recognize\_async} 传入的图像 shape 中提取，可自适应不同摄像头分辨率），得到像素空间向量后做 L2 归一化，其中 y 轴取反以符合屏幕坐标系向上为正的惯例。核心实现如代码\ref{code:pointing-direction}所示。

\begin{code}
\caption{食指指向方向计算}
\label{code:pointing-direction}
\lstset{style=codeblock}
\begin{lstlisting}
def _compute_left_direction(self, result):
    # 选取左手：两只手时按 handedness 筛选，否则直接用第一只
    target_hand = result.hand_landmarks[0]
    if len(result.hand_landmarks) == 2 and result.handedness:
        for i, h in enumerate(result.handedness):
            if h[0].category_name == "Left":
                target_hand = result.hand_landmarks[i]; break

    # 食指伸直判定：指尖(8) → MCP关节(5)，归一化距离 > 0.07
    tip, base = target_hand[8], target_hand[5]
    if ((tip.x - base.x)**2 + (tip.y - base.y)**2)**0.5 <= 0.07:
        return None

    # 方向向量：归一化坐标 → 像素空间 → 单位向量（y 轴取反）
    dx = (tip.x - base.x) * self._frame_width
    dy = -(tip.y - base.y) * self._frame_height
    mag = (dx*dx + dy*dy)**0.5
    return {"x": round(dx/mag, 3), "y": round(dy/mag, 3)} if mag > 0 else None
\end{lstlisting}
\end{code}

方向数据以 \texttt{input:move:x,y} 命令格式通过 TCP 中继直发 Unity，驱动 VirtualAgentDevice 的移动摇杆，进而控制旅人沿指向方向行走。与手势变化检测不同，方向检测运行于每帧（无节流），保证移动控制的实时跟手性。

\textbf{双手挥散检测}。该检测用于标题消散场景（详见本章标题动效部分），采用最简单的判定逻辑：若两只手均已检测到且手势类别均为 \texttt{Open\_Palm}，计算两手腕部（landmark 0）的归一化欧氏距离；当距离超过阈值 0.4 时判定为挥散动作，触发 \texttt{input:submit} 命令。冷却时间 1.5 秒防止重复触发。实现如代码\ref{code:sweep-detect}所示。

\begin{code}
\caption{双手挥散检测：Open\_Palm + 距离阈值 + 冷却}
\label{code:sweep-detect}
\lstset{style=codeblock}
\begin{lstlisting}
def _detect_sweep(self, result):
    if len(result.hand_landmarks) != 2:
        return
    if not result.gestures or len(result.gestures) != 2:
        return
    if (result.gestures[0][0].category_name != "Open_Palm"
            or result.gestures[1][0].category_name != "Open_Palm"):
        return

    w0, w1 = result.hand_landmarks[0][0], result.hand_landmarks[1][0]
    dist = ((w0.x - w1.x)**2 + (w0.y - w1.y)**2)**0.5
    if dist < 0.4:
        return

    now = time.time()
    if now < self._sweep_cooldown_until:
        return
    self._sweep_cooldown_until = now + 1.5
    for cb in self._sweep_callbacks:
        cb()
\end{lstlisting}
\end{code}

上述三层检测的输出通道各不相同：手势变化结果以 \texttt{omni\_type: "hand\_gesture"} 文本消息发送至 EchoAgent，作为高层交互决策的触发信号；指向方向以 \texttt{input:move} 命令经服务端中继直发 Unity，绕过智能体决策环路以确保低延迟；挥散动作以 \texttt{input:submit} 命令发往 Unity，经 AgentCommunicator 校验面部在场后触发标题消散动画。

\subsubsection{面部表情数据采集与节流}

面部感知由 FaceRecognizer 类实现，基于 MediaPipe FaceLandmarker 模型（\texttt{face\_landmarker.task}），开启 \texttt{output\_face\_blendshapes=True} 以输出 52 维面部形变系数（blendshapes）——如 \texttt{browInnerUp}（眉心抬起）、\texttt{mouthSmileLeft}（左嘴角上扬）等，每项取值 $[0, 1]$。鼻尖关键点（landmark 1）坐标作为面部空间位置参考，用于后续的面部出现/消失检测。

52 维形变系数若以 30 fps 逐帧全量上报，将产生极大的网络与智能体处理开销。FaceRecognizer 的核心设计在于双重节流机制，使推送频率自适应于表情变化的实际节奏。第一重为信号过滤：仅保留置信度高于 0.1 的形变系数，滤除低置信度噪声；第二重为变化阈值：计算当前帧所有活跃形变系数的均值，仅当该均值相较上次上报值的变化幅度超过 0.15 时才进入候选；第三重为最小间隔：两次上报之间至少间隔 500 ms。仅当后两重条件同时满足时，才将形变数据通过回调向外发送。双重节流的核心逻辑如代码\ref{code:face-throttle}所示。

\begin{code}
\caption{面部形变系数双重节流}
\label{code:face-throttle}
\lstset{style=codeblock}
\begin{lstlisting}
# 仅保留 score > 0.1 的 blendshapes
blendshapes = {
    cat.category_name: round(cat.score, 3)
    for cat in result.face_blendshapes[0]
    if cat.score > 0.1
}

# 双重约束：均值变化 > 0.15 且距上次发送 >= 500ms
current_mean = sum(blendshapes.values()) / len(blendshapes) if blendshapes else 0.0
now = time.time()
if abs(current_mean - self._last_blendshape_mean) > 0.15:
    if (now - self._last_callback_time) * 1000 >= 500:
        self._last_blendshape_mean = current_mean
        self._last_callback_time = now
        for callback in self._result_callbacks:
            callback(face_result)
\end{lstlisting}
\end{code}

这一设计的效果是：面无表情时几乎不产生推送，表情丰富时约每秒 2 次——在信息完整性与资源开销之间取得了平衡。面部形变数据以 \texttt{omni\_type: "face\_blendshape"} 事件格式发送，交由 EchoAgent 结合叙事上下文进行情绪语义推理。此外，FaceRecognizer 同时监测 \texttt{face\_landmarks} 的有无，在面部进入或离开摄像头视野时触发在场状态变化回调，Unity 端据此控制开场动画的启动时机。

\subsubsection{多线程事件上报架构}

感知子系统的OpenCV 的 \texttt{cv2.imshow} 与 \texttt{cv2.waitKey} 必须在主线程调用。而 MediaPipe 的 LIVE\_STREAM 模式将检测结果派发至其内部的回调线程，TCP 通信又依赖 asyncio 事件循环在独立线程中运转。因此系统采用三条线程协同工作：主线程仅负责 OpenCV 预览窗口渲染——调用 \texttt{get\_latest\_frame()} 获取最新帧，叠加手部骨架、手势标签、FPS 计数与面部鼻尖标注后显示。不参与识别或网络操作。摄像机线程以守护线程形式运行，尽可能高的帧率从摄像头读取帧、水平镜像翻转、BGR 转 RGB 后，将 RGB 图像与毫秒时间戳依次分发给所有已注册的帧回调——即 HandsRecognizer 与 FaceRecognizer 的 \texttt{recognize\_async} 方法。这种“一帧多发”的设计使两个识别器共享同一路视频源，避免了多摄像头或帧拷贝的开销。TCP 事件循环线程运行 asyncio 事件循环，承载 TcpClient 的全部网络收发。所有 \texttt{send\_text}、\texttt{send\_command} 等操作必须在此线程中串行执行以保证线程安全。

三条线程之间的桥接是架构的关键。MediaPipe 回调线程中产生的手势、方向、面部结果不能直接操作 TCP 连接——它们位于错误的线程。解决方式是通过 \texttt{asyncio.run\_coroutine\_threadsafe()} 将发送协程从 MediaPipe 回调线程调度至 TCP 事件循环线程。\texttt{main.py} 中定义的桥接函数如代码\ref{code:thread-bridge}所示。

\begin{code}
\caption{跨线程桥接：从 MediaPipe 回调到 TCP 事件循环}
\label{code:thread-bridge}
\lstset{style=codeblock}
\begin{lstlisting}
def handle_hand(r):
    asyncio.run_coroutine_threadsafe(on_hand(r), loop)

def handle_direction(direction):
    asyncio.run_coroutine_threadsafe(
        client.send_command(f"input:move:{direction['x']},{direction['y']}", "unity"),
        loop,
    )

def handle_sweep():
    asyncio.run_coroutine_threadsafe(
        client.send_command("input:submit", "unity"), loop
    )
\end{lstlisting}
\end{code}

TcpClient 在连接建立后通过 \texttt{on\_connected} 事件自动发送注册消息（\texttt{client\_type: "mediapipe", modules: ["hands", "face"]}）；若连接因服务端重启或网络波动断开，TcpClient 以指数退避策略（初始 1s，每次翻倍至上限 30s）自动重连，重连成功后再次触发 \texttt{on\_connected} 完成重新注册，整个过程无需人工干预。MediaPipe 客户端同时持续监听服务端下发的控制指令——例如 \texttt{hand\_direction:on/off} 用于远程开关指向检测功能——通过 \texttt{on\_command} 回调处理。

场景中任何脚本均可通过 \texttt{GameRoot.Instance} 访问这些全局服务，无需 \texttt{FindObjectOfType} 等开销较大的查找，也避免了模块间直接相互引用的耦合。GameStateManager 是这一架构中的编排中枢，同时实现了 ISaveProvider 接口。其内部维护一个标记 \texttt{[System.Serializable]} 的私有结构体，包含 ChapterState 枚举（Origin / Colony / Deepflow）与 EchoTitleActive 布尔量两个字段，属性 CurrentChapter 与 EchoTitleActive 均直接委托至结构体的对应字段，CaptureState() 直接返回该结构体，RestoreState() 通过类型匹配还原——以单一结构体实例作为唯一序列化后端，消除了字段与状态快照之间的数据冗余。在输入管控方面，GameStateManager 持有 Player\_Actions 的 InputActionAsset 引用，通过只禁用 Player 映射（Move、Sprint、Note*）而保留 UI 映射（Submit、Navigate 等），使系统在标题阶段可屏蔽角色移动等游戏操作，但仍能响应提交键以触发标题消散。在事件编排方面，其于 Start() 中集中完成三项初始化：禁用 Player 输入、订阅 EchoTitle 的 OnDismissComplete 事件（置 EchoTitleActive 为 false 后恢复全局输入）、订阅 AgentCommunicator 的 OnHandSweepGesture 事件（检查 FacePresent 后调用 EchoTitle.Dismiss()），使状态变迁的完整链路可在一处追踪。

\subsubsection{Unity端AgentCommunicator}

AgentCommunicator 作为 GameRoot 的子组件承担 TCP 客户端角色。启动时异步连接至服务端并发送注册消息，随后在后台 Task 中运行接收循环，按长度前缀协议解析入站消息，根据消息类型分派至对应回调。

在发送侧，\texttt{SendRawAsync} 方法使用 \texttt{SemaphoreSlim(1,1)} 作为发送锁，确保同一时刻仅有一个异步任务持有网络流的写入权，避免多协程并发写入导致的 TCP 数据交错。所接收消息通过 \texttt{SynchronizationContext.Post()} 投递至 Unity 主线程执行回调，符合 Unity 的单线程执行模型。

AgentCommunicator 还负责处理截图请求：当收到 \texttt{request:screenshot} 指令时，在帧末尾调用 \texttt{ScreenCapture.CaptureScreenshotAsTexture()} 获取当前画面，编码为 JPEG 并以 Base64 字符串回传，同时将截图缓存至本地持久化路径供调试使用。

灯光模式分为基础模式与音符联动模式两类，均由 LedController 类统一封装。LedController 在初始化时通过 \texttt{neopixel.NeoPixel} 接管 GPIO 23 引脚上的 64 颗 WS2812 灯珠，对外暴露模式切换与音符联动两类接口。NeoPixel 库提供了像素级的 RGB 色彩控制能力——\texttt{pixels[i] = (r, g, b)} 可单独设置第 $i$ 颗灯珠的颜色，\texttt{pixels.fill(color)} 则将全部灯珠统一置色，\texttt{pixels.show()} 将缓冲区刷入硬件。

基础模式中，控制系统利用 HLS 颜色空间来操作色彩变化，而非直接操作 RGB 分量。HSL色彩空间包含色相（Hue）、亮度（Lightness）和饱和度（Saturation）这三个分量，这样就可以将色相与亮度解耦，使色彩渐变逻辑的表达更为自然。具体而言：\texttt{chase}（追逐）模式循环遍历灯珠索引，每次仅点亮当前一颗灯珠后清空全带，利用视觉暂留形成光点移动的观感；\texttt{breathing}（呼吸）模式使用三角波函数 $b = 1 - |2x - 1|$（$x$ 在 $[0,1]$ 间线性推进）生成亮度曲线，将平滑变化的亮度与固定的低饱和度色相一同送入 \texttt{colorsys.hls\_to\_rgb}，使全带灯珠同步呈现柔和的明暗起伏；\texttt{rainbow}（彩虹追逐）模式同时维护 5 个色相各异的移动光点，每个光点后方拖曳 15 颗渐暗的灯珠——拖尾的亮度通过 \texttt{fade} 系数从近到远递减，光点位置每帧前进 2 颗灯珠，同时所有色相缓慢旋转，产生流动的彩虹拖尾效果。

以上动态模式均运行在独立守护线程（daemon thread）中：每次切换模式时，先通过 \texttt{threading.Event} 终止上一线程，再为新效果启动新线程，保证模式切换即时响应且不阻塞 TCP 指令接收。

音符联动模式直接利用 \texttt{music\_notes\_pixels\_map} 定位对应灯珠。\texttt{gain\_note} 遍历映射中的索引集合并点亮目标灯珠；\texttt{play\_note} 在此基础上加入“灭—亮—灭—亮”的短暂闪烁序列，形成与虚拟场景中音符演奏同步的视觉伴随反馈。LedController 的核心结构如代码\ref{code:led-controller}所示。

\begin{code}
\caption{LedController 灯光控制器核心实现}
\label{code:led-controller}
\begin{codebox}
class LedController:
    def __init__(self, pixel_pin=board.D23, num_pixels=64, brightness=0.2):
        self.pixels = neopixel.NeoPixel(
            pixel_pin, num_pixels, auto_write=True, brightness=brightness)
        self._stop_flag = threading.Event()

    def _rainbow_chase_loop(self):
        num_heads = 5
        tail_length = 15
        positions = [0] * num_heads
        hues = [i / num_heads for i in range(num_heads)]
        while not self._stop_flag.is_set():
            self.pixels.fill((0, 0, 0))
            for head in range(num_heads):
                for t in range(tail_length, 0, -1):
                    idx = (positions[head] - t) % self.pixels.n
                    fade = (1 - t / tail_length) * 0.9 + 0.1
                    r, g, b = colorsys.hls_to_rgb(hues[head], 0.5 * fade, 0.6)
                    self.pixels[idx] = (int(r * 255), int(g * 255), int(b * 255))
            self.pixels.show()
            time.sleep(0.03)
            for head in range(num_heads):
                positions[head] = (positions[head] + 2) % self.pixels.n
            hues = [(h + 0.008) % 1.0 for h in hues]

    def gain_note(self, note_name, color=(255, 255, 255)):
        for idx in music_notes_pixels_map.get(note_name, set()):
            self.pixels[idx] = color
        self.pixels.show()

    def play_note(self, note_name, color=(255, 255, 255)):
        indices = [i for i in music_notes_pixels_map.get(note_name, set())
                   if i < self.pixels.n]
        for _ in range(2):
            for idx in indices:
                self.pixels[idx] = (0, 0, 0)
            self.pixels.show(); time.sleep(0.1)
            for idx in indices:
                self.pixels[idx] = color
            self.pixels.show(); time.sleep(0.1)

    def _start_effect(self, effect_func):
        self._stop_flag.clear()
        t = threading.Thread(target=effect_func)
        t.daemon = True
        t.start()
\end{codebox}
\end{code}

第\ref{sec:traveler-design}节已从设计角度阐述了旅人形象的创作理念与概念设定。本节将从实现角度，完整描述旅人角色从二维概念图到Unity中可操控三维角色的技术流程，涵盖AI辅助3D建模、Blender骨骼绑定与关键帧动画、以及Unity动画状态机的构建。

旅人形象实现的第一步是将概念设计阶段的平面形象转化为三维模型。首先使用Google推出的NanoBanana图像生成模型，以第\ref{sec:traveler-design}节中ChatGPT生成的诗意概念描述为提示词，生成旅人的多视角的图片；随后将该图片输入字节跳动推出的Seed 3D模型，生成带PBR（Physically Based Rendering）材质的OBJ格式三维模型。Seed 3D能够从图像中推断几何结构与表面材质属性，输出的OBJ模型包含网格数据、UV映射以及漫反射、法线与粗糙度贴图，可直接导入Unity呈现正确的效果。

\subsection{旅人控制器实现}

旅人角色的移动由 TravelerController 组件驱动，该组件依赖 Unity 的 CharacterController 进行物理位移计算。在 \texttt{FixedUpdate} 中按固定时间步长执行重力施加、输入解析、旋转平滑与位移更新：读取 Input System 的 Move 动作获取二维输入向量，结合主摄像机的偏航角计算世界空间移动方向，通过 \texttt{Mathf.SmoothDampAngle} 实现角色朝向的平滑过渡；垂直方向累计重力加速度，着地时清零。TravelerController 的核心移动逻辑所示。

\begin{code}
\caption{TravelerController 核心移动逻辑}
\label{code:traveler-controller}
\lstset{style=codeblock}
\begin{lstlisting}
[RequireComponent(typeof(CharacterController))]
public class TravelerController : MonoBehaviour {
    [SerializeField] private InputActionReference moveActionRef;
    public float moveSpeed = 2.0f;
    [Range(0.0f, 0.3f)] public float rotationSmoothTime = 0.12f;
    private CharacterController _controller;
    private GameObject _mainCamera;
    private float _targetRotation, _rotationVelocity, _verticalVelocity;

    private void FixedUpdate() {
        ApplyGravity();
        Move();
    }

    private void Move() {
        Vector2 moveInput = moveActionRef.action.ReadValue<Vector2>();
        Vector3 inputDirection = new Vector3(moveInput.x, 0.0f, moveInput.y).normalized;
        if (moveInput != Vector2.zero) {
            _targetRotation = Mathf.Atan2(inputDirection.x, inputDirection.z) * Mathf.Rad2Deg
                            + _mainCamera.transform.eulerAngles.y;
            float rotation = Mathf.SmoothDampAngle(transform.eulerAngles.y, _targetRotation,
                ref _rotationVelocity, rotationSmoothTime);
            transform.rotation = Quaternion.Euler(0.0f, rotation, 0.0f);
            Vector3 targetDirection = Quaternion.Euler(0.0f, _targetRotation, 0.0f) * Vector3.forward;
            _controller.Move(targetDirection.normalized
                * (moveSpeed * Time.deltaTime * moveInput.magnitude)
                + new Vector3(0, _verticalVelocity * Time.deltaTime, 0));
        }
    }

    private void ApplyGravity() {
        if (!_controller.isGrounded)
            _verticalVelocity += Physics.gravity.y * Time.deltaTime;
        else
            _verticalVelocity = -.5f;
    }
}

EchoEventCenter 组件监听服务端下发的 \texttt{input:move:x,y} 格式指令，将解析出的方向向量写入 VirtualAgentDevice 的状态结构，通过 \texttt{InputSystem.QueueStateEvent()} 注入 Input System 事件队列，从而被 TravelerController 的 Move 动作绑定所消费。这一间接层使网络输入与本地键盘/手柄输入共享同一套 Input System 管线，无需在角色控制器中编写特殊的网络输入分支。

\subsection{基于动态着色器的视觉生成}

场景的视觉风格通过 Unity Shader Graph（URP 管线）构建的非真实感渲染（NPR）着色器实现。

着色器（Shader）是运行在 GPU 上可编程的图形程序，分为顶点着色器（Vertex Shader）
和片元着色器（Fragment Shader）\citing{feng2016unityshader}。如图\ref{fig:gpu-pipeline}所示，GPU 的渲染管线包括下面的工序：顶点着色器处理顶点的坐标转换信息，而片元着色器处理像素颜色数据计算信息。顶点着色程序从GPU 前端模块中获取到图元信息并执行顶点坐标的空间转换、 法向量的空间转换以及光照计算等操作，最终将计算的数据传输到指定的寄存器之中；随后片元着色程序从中提取所需要的数据，通常为纹理、坐标、光照信息等。并根据这些数据以及从应用程序传递而来的纹理信息执行每个片元的颜色计算，最后将处理后的数据信息传送至光栅操作模块。片元着色程序对每个片元进行独立的颜色计算，最终输出的值就是该片元最后呈现的颜色\citing{chen2024u3d}。

\subsubsection*{半透明抖动山峦}
\label{sec:ghost-mountain}

山峦的视觉表现由 GhostMountain 组件与山峦 Shader Graph 协同完成。着色器利用菲涅尔效应控制边缘发光——视线方向与表面法线夹角越大，菲涅尔因子越趋近于 1，使山峦轮廓呈现明亮的发光边缘，而正对视角区域保持较高透明度，整体呈现若隐若现的质感。顶点着色器中引入基于时间的连续噪声函数，对各顶点施加随机微小偏移，形成山峦轮廓的持续微颤效果。

着色器暴露三个 Uniform 参数：\texttt{\_WobbleSpeed}（抖动速度，控制噪声函数的时间频率）、\texttt{\_WobbleIntensity}（抖动强度，控制顶点偏移幅度）与 \texttt{\_FresnelColor}（菲涅尔边缘光的颜色）。\texttt{\_WobbleIntensity} 与 \texttt{\_FresnelColor} 可随系统情绪状态动态调整——低强度、冷色调对应迷茫氛围，暖色调对应锚定氛围，使山峦外观与情感叙事同步演变。半透明抖动山峦的实际渲染效果如图\ref{fig:ghost-mountain}所示。

\subsubsection*{风格化草地}

草地场景的动态效果本质上是草丛几何体顶点的规律性偏移，需要在顶点着色器上操作。为模拟随风摆动的动态，最核心的工具是连续噪声函数，其数学目标是构造一个连续可导、局部相关、全局随机的函数：$N(x, y, z) \in [-1, 1]$。相比真正的随机数，它满足：$\partial N / \partial x \neq 0$且变化平滑。如图\ref{fig:2d-noise}所示，这是一张满足上述要求的在二维空间上分布的噪声图像，将其灰度值线性映射到$[-1, 1]$区间即可表示风力大小。将噪声函数的位移值随时间移动采样，构建滚动纹理，即可作用于草丛的顶点偏移形成摆动效果。

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.2\textwidth]{pic/2d-noise.jpg}
  \caption{一种模拟风的二维连续噪声纹理}
  \label{fig:2d-noise}
\end{figure}

草地场景中存在成千上万的渲染实体，如果不加任何优化，将会造成严重的图形 API 调用开销。因此，本课题采用了 GPU Instancing 技术做性能优化。该技术通过合并相同网格的多次绘制调用，能够进一步减少 DrawCall 数量，从而在 CPU 与 GPU 之间实现更高效的任务分工与协作，最终促进整体帧率的提升与渲染流程的稳定。在 Unity 引擎中，可通过打开 Terrian 中的 Draw Instanced 选项、将渲染管线中 GPU Resident Drawer 设置为 Instanced Drawing 以及开启草丛材质的 Enable GPU Instancing 选项启用该技术。

\subsubsection*{体积雾}

Fog 组件通过持续更新雾材质的 \texttt{\_Offset} 向量，叠加正弦/余弦波动（不同频率与相位），产生缓慢漂移的雾气效果，增强场景的层次感与氛围感。


\subsection{交互场景视觉动效}

\subsubsection*{动态场景标题}

场景标题 EchoTitle 组件采用两阶段交互设计。

初始阶段，标题处于漂浮态（Floating）：利用柏林噪声（Perlin Noise）驱动各子文字对象的独立微动——每个文字在局部位置与旋转上叠加不同种子与频率的噪声扰动，产生有机、自然的漂浮感，呼应《回声之境》的整体美学基调。与此同时，GameStateManager 通过 InputActionAsset 仅禁用 Player 动作资产，保留 UI 动作资产，使系统在标题阶段屏蔽角色移动等游戏操作。

标题消散由两种同构的交互方式触发：其一为物理输入路径——参展者按下键盘提交键或手柄对应按钮，由 Input System 的 Submit 动作直接触发 EchoTitle.Dismiss()；其二为手势感知路径——MediaPipe 模块在检测到双手均为 Open\_Palm 手势且腕部归一化距离超过 0.4 时判定为挥散动作（\texttt{input:submit}），配有 1.5 秒冷却时间以避免重复触发，经 AgentCommunicator 校验面部已进入摄像头视野后触发。任一条件满足后，标题进入消散态（Dismissing）：各子文字以自身相对于标题中心的 YZ 平面方向为扩散轴，向外位移至 spreadRadius 半径处，叠加 X 轴随机抖动与各轴独立随机旋转，同时通过 URP Lit 材质的透明表面模式（\texttt{\_Surface=1}、\texttt{\_SURFACE\_TYPE\_TRANSPARENT}）与 MaterialPropertyBlock 逐帧降低 \texttt{\_BaseColor} 的 Alpha 通道，实现位置扩散、随机旋转与透明度渐隐的同步过渡，整个消散过程控制在 3 秒左右，视觉效果模拟文字被双手向外挥散的动态。消散完成后，EchoTitle 触发 OnDismissComplete 事件，GameStateManager 随即恢复 Player 映射的全局输入，参展者进入正式交互阶段。这一标题消散机制由 GameStateManager 担任编排中心，AgentCommunicator 提供手势指令事件，EchoTitle 专注动画执行，三者通过 GameRoot 单例协同工作。

\subsubsection*{音符UI动效}

四个音符（水滴、道路交错、海浪、风）的 UI 表现由 MusicNote 组件独立管理，每个音符维护获取态与未获取态。音符动效基于 DOTween 补间动画插件实现：获取音符时，执行缩放脉冲序列（交替放大至 1.3 倍与恢复原尺寸），同时从透明渐显至完全可见；水滴音符额外同步播放连接线淡入效果，以视觉化音符间的递进关系。演奏音符时，通过 \texttt{DOTween.Sequence()} 组合颜色过渡（切换为音符主题色）与发光脉冲循环（透明度在 0 与目标强度间交替），形成具有节奏感的演奏视觉反馈。

MusicNoteController 作为四个 MusicNote 的协调器，管理音符的获取顺序与演奏逻辑。四个音符须按序获得，控制器维护已获取音符计数，依次解锁下一音符。获取与演奏操作均通过 AgentCommunicator 向树莓派发送同步指令（\texttt{gain\_note:<type>}、\texttt{play\_note:<type>}），使实体灯光与虚拟音符动效保持同步。

\label{sec:state-driven-showcase}

本系统涉及多个模块之间的复杂交互，单纯以抽象的文字描述难以直观地呈现其完整的交互链路。因此，在讲述系统测试之前，本文首先列举三类典型的交互链路。

首先介绍状态驱动、相机控制、多模态输入链路。这些交互链路与\ref{sec:state-driven-camera}中的交互状态表\ref{tbl:chapter1-flow}保持一致。如图\ref{fig:state-driven-showcase}所示，当设备前无人时，相机会在Idle机位待命，此时其他的输入信号会被屏蔽。当用户面部进入装置的感知范围时，相机变为TopShowing状态，并提示用户张开双手挥散标题。此时如果用户离开，相机会重新回到Idle状态，而若用户做了挥散动作，标题会随之响应，播放散开的动画。随后，系统提示用户可伸出食指指向希望旅人行走的方向。手指信号会从MediaPipe端采集，经由TCP服务端转发到Unity端，接入统一的Input System管理，可与键盘、手柄无缝切换，驱动旅人向指定方向行走。旅人离开出生点石台后，相机切换为Following机位。Following机位会保证相机在预先定义的Spline曲线上移动，同时保持旅人在画面的中心。当旅人移动到水滴音符附近时，相机会再次切换为Showing状态，拉近并聚焦水滴音符。

\subsection{可观测性}

多模态交互系统的调试复杂度远高于传统单模块应用——手势识别、面部采集、智能体推理、Unity渲染和灯光控制分布在不同的进程甚至不同的硬件上，任何一个环节的异常都可能波及整体体验。为此，系统建立了一套从日志记录到链路追踪的完整可观测性体系。

在日志层面，系统基于Python标准库logging模块实现了按模块隔离的分层日志：服务端模块负责记录TCP连接建立、客户端注册、消息收发与中继转发等网络事件；智能体模块则记录消息队列的消费节奏、每轮推理的上下文规模、工具调用的类型与参数以及MiniMax TTS的合成结果。两条日志流同时输出至控制台与文件，文件按启动时间自动命名（echoagent\_YYYYMMDD\_HHMMSS.log），统一保存于logs目录。日志格式采用“时间戳 + 模块名 + 级别”的结构，支持事后按时间范围检索与按级别过滤。在开发阶段，可通过命令行参数--log-level DEBUG开启调试级别，此时日志将额外输出完整的消息内容、队列积压状态与异常堆栈，为定位间歇性问题提供更细粒度的信息。

在链路追踪层面，系统集成了OpenTelemetry与Phoenix实现端到端的调用可视化。通过OpenTelemetry的LangChain Instrumentor对EchoAgent的推理流程进行自动插桩，每一次ainvoke调用、每一轮工具选择与执行都被完整记录，形成可回溯的调用链。Phoenix追踪面板（如图\ref{fig:phoenix-trace}所示）可在浏览器上通过本地端口访问，开发者能够直观观察VLM的Tool Calling决策过程、上下文窗口的变化曲线以及各工具函数的执行时序与耗时分布。这套追踪体系使原本黑箱化的智能体行为变得透明可分析，在开发阶段极大加速了Prompt调优与工具定义迭代的效率。

\section{交互体验评估}

本系统的交互设计理念与Phillips等人提出的基于大语言模型的目标导向交互框架\citing{phillips2025goal}存在可比较之处，在此做一个简要的对位分析。

在架构设计层面，Phillips的框架采用DLM（对话语言模型）与QALM（问答语言模型）的双模型架构，分别负责自然语言对话生成和基于谜题图的状态评估，实现了生成与决策的解耦。本系统虽采用单VLM架构，但通过Tool Calling机制实现了类似的功能分离：对话生成、场景理解与工具调用由同一模型在统一上下文中完成，逻辑上却是三个独立的认知环节。双模型架构在对话生成质量上有优势，单模型+工具调用则在跨模态理解与开发复杂度上更为友好。

在状态追踪机制方面，谜题图框架将交互场景建模为显式的有向图$G=(V,E)$，节点代表情境里程碑，边代表合法的状态转移路径，状态转换由预设的封闭式问题集驱动——这种显式建模使叙事引导具有高度的精确性与可控性。本系统则采用更为隐式的情感状态图（迷茫→锚定、碰撞→边界、敬畏→自由），状态推进不依赖预设问答，而是由EchoAgent综合当前手势、表情与场景事件进行综合判断后自主决策。前者的优势在于状态转换的可预测性，适合任务导向的交互场景；后者的优势在于对模糊情境的容忍度，更适合情感导向的展览体验。

在交互范式的覆盖范围上，两套方法代表了不同的设计哲学。谜题图框架允许在结构化叙事框架内进行自由对话，强调“强自主性”——这与游戏设计中“涌现式玩法”的思路一脉相承。本系统则通过情感状态引导与自适应反馈，在保持叙事连贯性的前提下支持个性化探索，更接近展览设计中“情感化体验”的追求。前者的交互载体主要是文本对话，后者则将手势、表情、交互应用状态与物理灯光统一纳入交互回路，在模态的丰富性上更为全面。

总体而言，两种方法各有所长且存在清晰的互补空间。从谜题图框架中引入更精细的显式状态追踪，可以提升本系统叙事引导的精确性；反之，谜题图框架若扩展多模态感知与物理反馈能力，也将使展览场景中的交互体验更为丰富。二者的融合——双模型架构的对话生成优势加上本系统的多模态协调能力——是未来构建更强大交互系统的一个值得探索的方向。


\chapter{总结与展望}


\section{主要工作回顾}


本文围绕“面向实体展览的沉浸式多模态交互系统”这一课题，完成了一套从感知、理解到反馈的完整系统设计与实现，其核心工作事实上是实现了一套集成智能体的分布式通信框架。回顾全文，主要完成了以下工作：

\begin{enumerate}

\item 系统架构设计与实现：设计了“感知层—理解层—反馈层”的三层星型拓扑架构。感知层整合了MediaPipe手势识别、面部形变系数采集与Unity交互应用状态上报三个独立感知通道；理解层基于大语言模型构建了EchoAgent智能体，通过Deep Agents框架实现Tool Calling能力；反馈层由Unity虚拟场景渲染与树莓派LED灯阵物理装置构成，实现了虚拟与现实的双重输出。

\item 自定义通信协议与并发服务：设计并实现了基于长度前缀的JSON TCP通信协议，支持文本、图像、命令与注册四种消息类型，以及客户端间中继转发机制。基于Python asyncio实现了EchoServer并发服务端，统一管理Unity、MediaPipe、树莓派与调试四类客户端的连接与消息路由。

\item 智能体工具调用体系：为EchoAgent定义了五个工具函数——通用消息发送、Unity截图请求、LED灯光控制、音乐播放控制与MiniMax TTS语音合成——覆盖了从设备控制到多模态输出的完整能力集。智能体以5秒轮询间隔从共享消息队列批量获取感知数据，交由大语言模型综合推理后自主调用工具。

\item 物理灯光联动装置：基于树莓派与WS2812可编程LED灯阵实现了实体灯光控制，支持追逐、常亮、彩虹渐变、呼吸四种预设模式以及音符联动反馈，将虚拟场景的氛围变化延伸至物理展览空间。

\item 交互应用原型开发：在Unity引擎中完成了《回声之境》交互应用的基础框架，实现了旅人角色的移动控制、场景切换、音符触发与状态机管理，以及手势指向驱动的输入映射。

\item 可观测性体系建设：集成了OpenTelemetry与Phoenix链路追踪，实现了从智能体推理到工具调用的全链路可视化；建立了分层日志系统，支持按模块、时间范围与日志级别的灵活查询。
\end{enumerate}


\section{创新点}


在上述工作中，本课题形成了以下创新点：

\begin{enumerate}

\item 以智能体为认知核心的展览交互范式：不同于传统展览装置中“触发—响应”的预设规则模式，本系统将大语言模型智能体置于决策中枢位置，使其统一接收多源感知信息、综合推理并自主调用工具，形成“感知—理解—反馈”的认知闭环。这使得系统能够根据参展者的手势、表情与交互历史做出情境化的动态响应，而非机械地执行固定脚本。

\item 虚实双重输出的协同反馈机制：同一智能体决策指令同时驱动虚拟场景的视觉变化与实体LED灯阵的灯光效果，使屏幕内的渲染与物理空间的光影协调一致，将沉浸感从画面内部延伸至参展者的身体周边。

\item 零训练部署的轻量化方案：系统直接利用大语言模型的零样本推理能力与Tool Calling机制，无需针对特定展览场景收集标注数据或训练专用模型，仅通过系统提示词与工具定义即可适配不同交互需求，降低了在展览场景中部署智能交互系统的技术门槛。
\end{enumerate}


\section{不足与反思}


尽管上述工作基本实现了课题设定的目标，但在实际开发与测试过程中，也暴露出若干不足，值得在后续工作中加以反思与改进。

\begin{enumerate}

\item 交互应用内容深度不足：本课题虽然完成了技术框架的搭建，但其配套交互应用《回声之境》的叙事内容与交互关卡远未达到设计预期。前期规划的不同章节的交互逻辑，包括其中的锚点谜题和分支区域仅完成了初步的概念设计，而并未在Unity中实际实现。系统当前能够完成手势输入、场景切换与灯光联动等基础交互，但缺乏真正的叙事推进与关卡挑战。更深层的问题在于，可玩性并非纯粹的技术问题——巧妙的谜题设计、有节奏的关卡推进、对参观者情绪的引导，以及如何在数十秒内让路人产生好奇心，这些面向体验的能力恰恰是数字媒体技术专业区别于一般工程技术工作的关键，却未能在本课题中得到充分体现。这使得整个系统的技术价值缺乏内容层面的承托，多模态交互机制也未能得到充分的场景验证。

\item 模块间耦合松散：系统由多个独立运行的子模块组成，模块间的通信协议虽然定义完备，但各模块的启动时序、异常恢复与状态同步缺乏统一的编排机制。这导致整套系统虽然能够在开发者的手动配置下跑通演示流程，却难以打包迁移至其他设备环境，也难以在外快速启动。此外，系统在无人值守的展览场景下所需的鲁棒性机制，如手势识别过程中的中断与重置、关卡进度的持久化与回溯也尚未完整实现。若要真正将本系统部署到实际的博物馆等实体展览场景中，仍需大量外围的开发和调试工作。

\item 未能充分利用全模态模型的能力：系统当前的多模态感知通路实际上是将手势、表情与场景状态分别编码为文本或图像后送入大语言模型，而非真正的全模态理解。近年来发布的Qwen3.5-Omni\citing{qwen35omniblog}、Kimi-K2.5\citing{kimik25}等模型已原生支持文本、图像、音频、视频的端到端联合推理，若能将其替换为EchoAgent的底座模型，不仅可以简化多模态数据的预处理流程，更可能使智能体直接从音频流中感知参展者的语气变化、从视频流中理解连续的行为意图。

\item 情绪感知链路缺乏快速响应通道：当前面部识别模块仅输出MediaPipe的52维形变系数（blendshapes）原始数据，情绪分类与理解完全交由EchoAgent完成。这一设计简化了感知层，但也导致两个后果：智能体推理延迟在秒级，无法满足灯光和着色器等毫秒级响应的需求；形变系数为底层几何特征，智能体对中性或混合表情的边界判断缺乏稳定锚点。

\item 智能体的决策可解释性不足：尽管系统集成了Phoenix链路追踪工具，但大语言模型在Tool Calling中的推理逻辑本质上仍是黑盒。在面向普通观众的展览场景中，难以向参观者解释系统为何在某一时刻选择了特定的灯光模式或音乐切换，这在某些需要透明性的公共展览中可能构成信任障碍。
\end{enumerate}


\section{未来展望}


基于上述反思，后续工作可从以下几个方向展开：

\begin{enumerate}

\item 补全交互应用的叙事内容：将第三章中设计的关卡逻辑在Unity中逐一实现，使水滴、道路交错、海浪、风四个音符的获得过程成为真正可玩的交互关卡，让技术框架与叙事内容相互匹配。

\item 引入全模态模型作为认知底座：将EchoAgent的基座模型替换为Qwen3.5-Omni这样的原生全模态模型，使其能够直接处理音频流、视频流等多模态输入，减少预处理环节，提升智能体对参展者整体状态的理解深度。

\item 构建模块编排与容错机制：引入统一的启动编排、健康检查与异常恢复策略，确保MediaPipe、EchoAgent、Unity与树莓派在任意启动顺序下均能建立稳定的通信链路，并能在单个模块故障时优雅降级而非整体崩溃。

\item 建立快慢双通道情绪感知架构：在感知层增加一个基于规则映射的轻量级快通路，从形变系数直接计算情绪倾向（如积极/中性/消极）并低延迟推送至灯光与着色器；同时保留EchoAgent的深度理解慢通路用于叙事推进与音乐切换等高层决策。
\end{enumerate}

在结束本文之前，我想聊一个话题：“在AI技术不断突破的今天，你心中的下一代游戏体验？”这个问题来自米哈游（上海米哈游科技股份有限公司）创始人刘伟2026年4月在上海交通大学的演讲。

尽管我做的这个课题并非游戏，但如果你有心认真读完，一定能感受到我其实只是在借实体展览这个由头来讲述，而我真正想做的，就是一款个性化的自我表达的叙事游戏。游戏里的这个所谓旅人，其实就是大学本科的我的一个化身。旅人在初域·未定之原的迷茫，其实就是我在初入大学时的感受，其实也带着些对高中时候失去的白月光的迷惘；旅人在聚落群·彼方的光影之城感受到的错乱，其实也是我在加入社团、组织、参加合唱团，遇到了许多的人，也结交了许多朋友，谈了一场恋爱，又经历了分手，这些种种，都像嘈杂、交错的十字路口，来往者行色匆匆。我逐渐在这些复杂的感受中流浪，在这些交错的道路中寻找到自己的方向，也慢慢学会了感受自己和他人的情绪。最后我终于走出这片混沌，开始迈向人生的下一个阶段。我开始复习408和高数准备考研、开始参加暑期活动，又开始结交新的一批来自不同圈子的朋友，最后我莫名其妙地成功保研，就连我自己都觉得十分神奇。这一部分就对应了《回声之境》中的深流之径·未被触及的知识海。我发现，我学得越多，未知也越多。其实这整个毕设都是用来回答这个问题的，我在这里杂糅了来自很多不同学科领域的知识，试图用此来让这些分流的潮水聚合。

好，我自己的经历就先讲到这里。让我们回到一开始的问题。大伟哥，即刘伟，他给出的答案是什么呢？他说，接下来在AI这个时代，游戏体验会有一个我们能够预见到的变化，就是完全个性化的游戏体验。他用一部美剧《西部世界》来举例——一个相同的世界观，但每次体验的时候，故事完全不一样，他如是讲道。他说，我们今天的游戏，因为生产成本，整场所有人的游戏体验都是一样的，但接下来因为有了AI，它可以理解你的行为，它能够给千人千面的游戏体验。我听到这个观点的时候被深深触动了，我想到米哈游近年来所做的一些其他工作，其实就是我在论文的前两章引用到的Whispers from the Star、LPM 1.0表演模型、Lumine，它们似乎都悄然在向着这个目标前进。

我将智能体和现实空间引入到交互叙事中，莫不是也盼着千人千面的游戏体验呢？当然，我深知我做的这东西只能算是一个勉强看得过去的demo。如果要真正达到我理想的那样一个叙事游戏，那工作量差的可不是一点半点。

最后，我把我前一段时间，临近毕设收尾时的一些想法放在下面。

\section{环境配置}

本系统框架一共分为EchoAgent智能体、TCP服务端、Unity客户端、MediaPipe感知、灯光控制这五个模块以及一个专用调试客户端。TCP服务端和Unity客户端为必需，其他可根据实际的应用需要选择性部署。除此以外，开发者也可基于本系统的自定义TCP协议定制开发其他的客户端。其中Unity客户端必须运行在具备高性能GPU的计算机上，灯光控制模块必须运行在具备PWM输出能力的开发板上，而其他客户端可由开发者自由选择配置在何种设备上，只要这些程序所运行的平台共处同一局域网，可通过TCP相互通信即可。

\section{使用说明}

\subsection{启动各模块}

在所有模块中，EchoAgent智能体模块和TCP服务端模块应首先启动。这两个模块属于同一项目，在同一进程中运行。进入项目目录，激活虚拟环境后执行：

\begin{verbatim}
uv run main.py --log-level DEBUG
\end{verbatim}

其中\texttt{--log-level DEBUG}开启调试级别日志，输出完整消息内容与队列积压状态，便于开发阶段观察系统运行细节；生产环境可省略此参数。智能体

其余模块的启动顺序无严格依赖——MediaPipe感知模块、灯光控制模块和调试客户端可在任意时刻连接至已运行的TCP服务端，注册后即可加入系统协同工作。

启动MediaPipe感知模块，进入项目目录后执行：

\begin{verbatim}
uv run main.py --preview
\end{verbatim}

\texttt{--preview}参数启用摄像头预览窗口，实时显示手势识别结果与方向向量。如需连接至非本机的TCP服务端，可通过\texttt{--host}与\texttt{--port}参数指定目标地址；如需启用左手方向指示功能，可附加\texttt{--left-hand-direction}参数。

Unity客户端在Unity编辑器中打开即可运行。Unity客户端启动后会自动连接至同网段的TCP服务端，无需额外配置网络参数。

灯光控制模块运行在树莓派上，需先完成接线与PWM通道配置，然后在项目目录中激活虚拟环境并运行灯光控制脚本。

\subsection{调试观测}

本系统内置了多层次的调试与可观测性支持，覆盖日志记录、链路追踪与专用调试工具三个维度。

调试客户端基于Rust编写，进入项目目录后执行\texttt{cargo run}，编译并启动后会同时在端口8080上提供基于浏览器的可视化调试界面。

在日志层面，系统基于Python标准库\texttt{logging}模块实现按模块隔离的分层日志：TCP服务端模块记录连接建立、客户端注册、消息收发、中继转发等网络事件；智能体模块记录队列消费节奏、推理上下文规模、工具调用参数与TTS合成结果。日志同时输出至控制台与文件，文件按启动时间命名（\texttt{echoagent\_YYYYMMDD\_HHMMSS.log}）并保存在\texttt{logs}目录下，通过命令行参数\texttt{--log-level DEBUG}可开启调试级别日志。

在链路追踪层面，系统集成了OpenTelemetry与Phoenix实现端到端调用可视化。通过OpenTelemetry的LangChain Instrumentor对EchoAgent推理流程自动插桩，每次\texttt{ainvoke}调用、工具选择与执行均被完整记录，形成可回溯的调用链。Phoenix追踪面板在浏览器中通过本地端口访问，可观察VLM的Tool Calling决策过程、上下文窗口变化以及各工具函数的执行时序与耗时分布。

在专用工具层面，基于Rust开发的调试客户端\texttt{echo\_client}提供了可编程的Rust库与基于warp框架的WebSocket-to-TCP桥接服务器。配套的浏览器调试界面支持选择客户端类型、构造自定义消息内容、指定中继目标，并实时展示所有收发日志。开发者可通过调试客户端向系统内任意模块发送命令或模拟消息，无需依赖完整的硬件环境即可验证通信逻辑。此外，在树莓派端可通过WiringPi库的\texttt{gpio readall}命令查看全部40个引脚的BCM编号、物理引脚号及输入输出状态，排查接线问题；通过\texttt{lsof -i :65432}命令可查看当前TCP服务端的连接状态。

\subsection{拓展新模块}

本系统采用自定义的TCP应用层协议作为模块间通信的统一规范，开发者可基于此协议定制开发新的客户端模块，以扩展系统的感知输入或输出能力。

协议采用4字节大端序长度前缀 + UTF-8编码JSON载荷的帧格式。每条消息以4字节大端序无符号整数指示后续JSON载荷的字节数，接收方据此准确读取完整帧。JSON载荷的核心字段包括：\texttt{type}（消息类型，取值为\texttt{text}、\texttt{image}、\texttt{command}、\texttt{register}）、\texttt{data}（载荷内容）、\texttt{client\_type}（发送者标识）、\texttt{request\_id}（请求追踪标识，UUID格式）、\texttt{relay\_to}（中继目标类型，指定消息直接转发至某类客户端）。

新模块与系统建立通信的流程如下：（1）通过TCP连接至服务端端口65432；（2）发送一条\texttt{register}类型消息，携带自身的\texttt{client\_type}标识；（3）注册完成后，即可按协议格式收发消息，参与系统协同。若新模块为感知输入型（类似MediaPipe），主要向服务端发送\texttt{text}或\texttt{image}类型消息；若为执行输出型（类似灯光控制模块），主要接收并响应\texttt{command}类型消息；也可同时兼具两种角色。

命令体系采用三级前缀约定以区分语义：\texttt{request:}前缀表示请求型命令，需要接收端响应并携带\texttt{request\_id}；\texttt{input:}前缀表示输入注入型命令，模拟用户操作行为；无前缀者为直接控制命令，即发即忘。新模块在设计自身命令时建议遵循此约定，以保持系统命令体系的一致性。具体命令格式与字段定义可参见正文第4章中的协议表与命令表。

\section{《回声之境》应用使用方法}

\subsection{应用简介}

《回声之境》是本系统框架配套的沉浸式多模态交互应用，以旅人的旅程为叙事主线，引导参展者完成从自我迷茫走向全然自由的体验历程。应用全程无需手持控制器——参展者通过手势控制角色移动、以面部表情影响场景变化，虚实联动的LED灯阵和音乐旋律共同构成完整的多感官反馈闭环。

体验设计为三个章节：第一章“初域·未定之原”聚焦自我认知，通过指尖指向引导旅人穿越迷雾中的山峦，以捏合手势获取水滴音符；第二章“聚落群·光影之城”聚焦人际边界，场景建筑随参展者情绪舒展或扭曲；第三章“深流之径·知识海”聚焦知识接纳，潮水随认知碎片收集而涨落，最终在自由探索中解锁全部音符。目前第一章的基础交互框架已实现，第二、三章的交互机制仍处于设计阶段。

\subsection{体验前准备}

在开始体验前，请确保各模块已按A.3.1节所述完成启动：EchoAgent智能体、Unity客户端、MediaPipe感知模块均已正常运行，灯光控制模块（树莓派+WS2812灯带）已就绪。硬件方面，请检查摄像头正对体验区域，显示屏画面正常输出，LED灯带已按接线要求连接。

体验区域建议预留约1m $\times$ 2m的站立空间，使摄像头能够稳定捕捉参展者的上半身动作与面部。四个音符实体木牌悬挂于展台一侧，参展者在体验过程中可随时触摸以参考音符形状。

\subsection{体验流程}

需要说明的是，受限于开发周期，目前《回声之境》仅在Unity中实现了第一章的基础交互框架，包括标题交互、手指指向行走与音符触发，而后续章节的锚点谜题、情绪折射、知识潮等交互机制仍处于设计阶段，尚未在引擎中实际落地。下文所述为完整的设计体验流程。

\textbf{初始阶段}。体验开始前，屏幕显示标题画面，系统处于非交互状态。参展者走近摄像头，使面部进入传感器识别范围后，双手向两侧挥散即可触发标题消散动画——此时旅人从迷雾中浮现，系统开始接受交互输入。如手势识别未能触发，可按下键盘回车键作为替代方式。

\textbf{第一章：行走与奏响}。标题消散后，参展者伸出食指，指尖朝期望的方向短暂停留——MediaPipe实时计算食指指向向量，经TCP协议传输至Unity后驱动旅人沿该方向行走，缩回手指后角色自动停止。旅人行走至水滴音符附近时，摄像机会自动推近至水滴特写；参展者做出持续捏合手势即可触发音符获取事件，同时实体LED灯阵中对应音符区间的灯珠同步亮起。以上行走与音符触发逻辑已在Unity中完成实现。设计中的后续内容还包括：三条锚点路径（落石阶、无风谷、雾之界）分别对应过去、现在与未来三重自我锚定，全部激活后迷雾散尽，通往第二章的宽阔光路显现。

\textbf{第二章：情绪折射}。进入光影之城后，MediaPipe的面部表情识别持续监测参展者的blendshape系数，VLM智能体据此推断情绪基调并驱动场景建筑形态变化——喜悦使建筑舒展向上，悲伤使其低垂收敛，愤怒引发扭曲震颤。参展者需要在四个分支区域（回声交汇处、情绪风塔、镜像回廊、告别十字路）中收集碎片，每收集一处将使城市建筑趋于稳定。奏响“道路交错”音符可在自身周围构建视觉化的边界范围，过滤外界情绪干扰。

\textbf{第三章：知识海与自由探索}。前两章收集的音符在此汇聚。浅水区散布6枚认知碎片（观察、耐心、试错、连接、放手、接纳），每获取一枚，知识海的潮水上涨一级。集齐6枚后解锁“海浪”音符，进入深水区面对困惑、遗憾与无知三波情绪浪潮。最终触碰海心核，四音符合奏为完整旋律，解锁“风”音符，进入自由探索阶段——参展者可自由演奏四种音符，每种将改变整个世界的视觉形态。

\textbf{退出}。参展者离开摄像头识别范围后，系统自动进入待机状态，画面恢复至标题界面，等待下一位体验者。

\subsection{操作速查}

\begin{enumerate}
\item 双手向两侧挥散 —— 开启交互 / 触发场景转场
\item 食指伸出并指向方向 —— 控制旅人行走，缩回停止
\item 持续捏合手势 —— 触发音符获取与灯光联动
\item 面部表情自然变化 —— 影响场景建筑形态（第二章）
\item 键盘回车键 —— 替代手势触发转场
\item 键盘 1/2/3/4 键 —— 直接演奏水滴/道路交错/海浪/风音符
\end{enumerate}

\subsection{注意事项}

手势识别在均匀光照条件下效果最佳，请避免摄像头正对强光源或处于完全逆光位置。体验过程中请保持与摄像头约0.5--2m的距离，超出此范围可能导致手势识别精度下降。捏合手势需保持0.5秒以上方可触发音符奏响，避免短促的误触。LED灯带在灯珠全亮时发热明显，连续运行超过2小时后建议暂停散热；若使用树莓派5V引脚直接供电，请勿长时间保持灯珠全白高亮状态，以免超出引脚输出电流承载能力。

肢体活动范围请控制在摄像头视野内，尤其在做出挥散和指向动作时，手部尽量不超出画面边界。如遇旅人行走卡顿或方向偏移，可缩回手指等待片刻后重新伸出，系统将自动重新校准指向基准。\end{document}
